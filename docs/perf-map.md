## 2. Вердикт в трёх абзацах

**Стиль.** Из 4.4 мс доминирует одна статья: сопоставление селекторов —
линейный перебор всех правил всех листов на каждый узел, без индекса, без
корзин, без Bloom-фильтра (С1). ~134 правила × ~200 узлов = порядка 27 тысяч
попыток матча за полный рестайл, и ни одна не переиспользуется между кадрами.
Всё остальное в этой фазе — вторая по величине статья втрое мельче: цикл по
всем 101 свойству на каждом узле (С2) поверх хеш-таблицы на 101 свойство,
выделяемой каждому узлу (С3).

**Композиция.** Восемь миллисекунд не объяснены до конца, и это главный
остаток. Три механизма имеют подходящий масштаб: полная вёрстка каждого абзаца
на каждом кадре без кеша (К1) — единственная статья, растущая и с числом
текстовых узлов, и с числом глифов; ~33 повторных хеш-поиска стиля и ~10
поисков бокса на каждый узел по таблице в ~8 КБ, то есть промах кеша на каждый
зонд (К2); и то, что сцена объективно стала богаче — у клавиши появились фон,
рамка и радиус, которых в августе не было (К3). Но арифметика ни одной из трёх
не даёт 130 мкс на клавишу, поэтому честный ответ: **значительная часть этих
восьми миллисекунд не атрибутирована**, и первый шаг — не правка, а замер.

**Регрессия «вдвое» объяснена наполовину.** Опорное утверждение постановки
(«композиция в коде не менялась ни на байт») неверно: `git diff b791b971 HEAD`
по `scene_coordinator.rs` даёт 233 добавления / 235 удалений, и в сторону
удешевления (HashMap→FastMap, два обхода stacking слиты в один). Версия «вырос
рабочий набор стиля» тоже опровергнута историей: `COMPUTED_PROPERTIES` было 103
записи, стало 101, а custom-свойства из копии в каждом узле стали общими через
`Rc`. Остаётся К3 — сцена, которая после починки `var()` стала рисоваться
вдвое большим числом команд на клавишу при неизменном коде композиции. Механизм
подтверждён построчно, величина — нет.

## 3. Карта по фазам

### 3.0. Измерение

Эти четыре пункта не возвращают ни одной миллисекунды и должны быть сделаны
первыми, потому что без них остальные нечем ранжировать.

**М1. Часы фаз не охватывают кадр; `other` ноль арифметически.**

(`:337`). Правка: перенести `start()` в начало `run_frame`, `finish()` — в
конец, в `compose_phase` оставить только `mark_compose()`.

**М2. Граница style смещена: разрешение картинок записано в «стиль».**

**М4. Вывод не измеряется вовсе.** `kit/.../runtime/frame_phase_clock.rs:135-145`.
**класс:** дефект измерения, крупный. Растеризация, захват образа, блит и

### 3.2. Стиль — 4.2–4.8 мс

**С1. Сопоставление селекторов — линейный перебор всех правил всех листов на
каждый узел; индекса нет ни на уровне листа, ни на уровне набора.**
`kit/crates/domain/obscur-style/src/matching/style_matcher.rs:45`. **класс:** крупная.
`Stylesheet` — плоский `Vec<StyleRule>` (`stylesheet.rs:10`), никаких корзин по
правому простому селектору; `match_element_in` крутит
`for sheet { for rule { SelectorMatcher::matches_list(...) } }`. У клавиатуры
UA-лист 53 блока плюс 8 авторских листов (1251 строка CSS, 81 правило) —
порядка 134 правил на ~200 узлов, то есть ~27 тысяч попыток матча за полный
рестайл, ни одна из которых не переиспользуется между кадрами. Хуже: внутренний
цикл `for block_decl in rule.block()` (`:52-66`) входит в тело и для
НЕподошедшего правила — только чтобы прокрутить `source_order`, — так что
перебираются и все ~620 объявлений. Второй проход
`match_custom_properties_in` (`:80`) идёт по тем же правилам ещё раз, хотя и с
ранним `continue` на правилах без custom-свойств (`:88-90`).
**Почему это ответ фазы, а не клоны значений:** селекторы клавиатуры выписаны —
из ~81 правила практически все одиночный класс (`.key`, `.tool`, `.pick`,
`.suggestion`, `.chip`), лишь три с потомковым комбинатором. Индекс по правому
классу сократил бы 134 проверки на узел до двух-четырёх.
**Правка:** один раз на набор листов (там же, где сейчас `CascadeSheets::cascade`)
построить корзины `map<класс → Vec<rule_idx>>`, `map<id → …>`, `map<tag → …>`
плюс bucket универсальных; на узле опрашивать только корзины его классов, тега и
id. `source_order` сохраняется, если хранить в корзине глобальный индекс правила
и сливать по нему. Отдельно и независимо — одна строка перед внутренним циклом:
`if specificity.is_none() { source_order += rule.block().len(); continue; }`.

**С2. Разрешение идёт по всем 101 свойству на каждом узле, и две трети этой
работы не зависят от узла.**
`kit/crates/domain/obscur-style/src/computed/style_resolver.rs:154`. **класс:** средняя.
Цикл `for &property in COMPUTED_PROPERTIES` (`:152-168`) без раннего выхода
делает на каждое свойство: `cascaded_for` (промах в хеш-таблице узла — для ~80
из 101), затем либо `parent.get(property).cloned()` — второй хеш-поиск ПЛЮС
глубокий клон значения родителя (`:368`), либо `initial_value_of` —
конструирование значения, затем `uses_ch`, `absolutize_value` и вставку в
таблицу узла. Наследуемых свойств ~19 (`property_id.rs:441-471`), значит ~62
необъявленных ненаследуемых свойства на узле материализуют `initial`
поштучно — притом что ответ у ВСЕХ узлов один и тот же. Смягчения, которые
надо знать: `initial_value_of` возвращает `None` примерно для двадцати
свойств, и они в карту не кладутся; `cascaded_for` имеет ранний выход по
`is_logical_target()`/`has_logical()` (`logical_cascade.rs:62`), а логических
свойств в CSS клавиатуры нет вовсе.
**Правка:** разбить набор на три класса вместо одного цикла. Ненаследуемое и
необъявленное не хранить в узле совсем — `ComputedStyle::get` при промахе падает
в статическую таблицу `INITIAL`. Наследуемую часть держать одной
`Rc<InheritedRow>`: узел, не объявивший ни одного наследуемого свойства, делит
строку родителя указателем — ровно тот приём, что уже сделан для custom-свойств
на `style_resolver.rs:75-81`. Цикл вести по объединению «объявлено у узла» ∪
«изменилось у наследуемой строки».

**С3. `ComputedStyle` — хеш-таблица на 101 свойство у каждого узла, ~8 КБ

control-байт, память из арены, переиспользуемой между кадрами. Ни `size_of`, ни
счётчики промахов не измерялись — вся арифметика выше выведена из определений
типов.

**С4. У `Stylesheet` нет идентичности или версии, поэтому «те же листы?»

**С5. `Cascade::resolve` рождает четыре-пять контейнеров на узел, и один из них

**С6. Значение каждого выигравшего объявления копируется два-три раза за узел.**

### 3.3. Раскладка — ~0.9 мс

Вся фаза — 6% кадра, поэтому потолок любой находки здесь — доли миллисекунды.
Держите это в голове: механизмы ниже настоящие и на большой сцене станут
дорогими (§5), но сегодня они не то место, где лежат деньги.

**Р1. `ArrangePhase` перестраивает таблицу layout-стилей и таблицу
grid-шаблонов из ВСЕХ узлов даже на инкрементальном пути.**
`kit/.../runtime/arrange_phase.rs:89-123`. **класс:** средняя.
До того, как dirty-множество вообще прочитано (`:139-142`), фаза строит
`layout_styles_from` по всей карте computed (`layout_coordinator.rs:43-59` —
`computed.iter().map(...).collect()`, и на каждом узле `layout_style_from`
вычитывает порядка сорока свойств из его восьмикилобайтной таблицы), прогоняет
по ней четыре патч-прохода и отдельно `grid_templates_from` снова по всей карте.
Шесть проходов «на каждый узел» выполняются одинаково для `Full` и для
`Invalidated`; это ~9 тысяч холодных поисков за кадр только на первом проходе.
**Правка:** держать `LayoutStyles` и `GridTemplates` ретейном рядом с боксами и
патчить только узлы из грязного множества.

**Р2. `measure()` выбрасывает уже посчитанные боксы детей, и `arrange` заново
прогоняет тот же алгоритм на том же узле.**
`kit/.../orchestration/measure_pass.rs:177-179` против `arrange_pass.rs:195-208`.
**класс:** мелкая (для этой сцены; архитектурно — крупная).
`algorithm.layout` возвращает `LayoutOutput` с `size` + `child_boxes` +
`child_percent_bases`, а в кеш кладётся только `out.size()`. Ключ
(`measure_cache.rs:83-99`) включает все шесть чисел ограничений, а родитель мерил
ребёнка `loose(offer)`, тогда как arrange даёт `tight(измеренный размер)` —
разные ключи, промах по построению, поддерево мерится заново. Кеш меры работает
честно, он просто не может помочь.
**Правка:** хранить в `MeasureCache` весь `LayoutOutput` и спрашивать его в
arrange перед повторным `algorithm.layout`.

**Р3. `grid-template-columns: 1fr` заставляет мерить поддерево каждого элемента
лишний раз при нулевой ширине.**
`kit/crates/domain/obscur-layout/src/algorithm/grid_layout.rs:257`. **класс:** мелкая.
`grid_track_sizing.rs:183-185` объявляет `TrackSize::Fr(_) => kind == Kind::Min`,

объявляет по одному fr-треку на клавишу инлайном (`app/.../key_model.rs:167-175`),

`LayoutPhase::Full`, а `layout_coordinator.rs:215-221` на `None` делает
`cache.clear()` — и `Full` берётся на каждом кадре с `reconciled`
(`layout_classifier.rs:66-68`), то есть на каждом нажатии.

**Р4. Мелочи раскладки.** `formatting_context.rs:38` — `children_of` строит
`Vec<LayoutChild>` с `LayoutStyle` (~200 байт) по значению, а `in_flow_children`
(`:65`) и `partition_children` (`:77`) зовут его заново и перекладывают

`layout_eviction.rs:45` — чтобы вытеснить записи для одного узла, строится с нуля

ранний выход на `:24-29`, так что «на каждом инкрементальном кадре» — неверно).
`measure_cache.rs:12` — единственная горячая карта фазы, оставшаяся на

`hit_testing.rs:236` — `logical_depth` поднимается до корня без мемоизации на
каждый узел при перестройке hit-индекса, и индекс перестраивается безусловно
(`arrange_phase.rs:165`), потому что `relaid_out` считается как `!boxes.is_empty()`
и потому истинно всегда. **класс всех:** мелкая.

## 4. Порядок работ

Считано по отношению «сколько миллисекунд вернёт / чем рискуем», а не по красоте
правки.

**Сначала — о риске.** Правки делятся на два класса, и они не равны. Первый:
чистая механика без состояния между кадрами — поднять поиск из хелпера в цикл,
сменить тип возврата, добавить `with_capacity`, заменить `Vec` на `Rc`. Такая
правка либо компилируется и даёт тот же результат, либо не компилируется; хуже
падения быть не может. Второй: всё, что трогает инвалидацию — кеш вёрстки
абзаца (К1), флаги «в дереве нет позиционированных узлов» и «нет
scroll-контейнеров» (К4, К8), кеш paint-юнита узла, ретейн `LayoutStyles` (Р1).
Здесь ошибка не роняет программу — **на экране остаётся старое**, и заметит это
не тест, а пользователь через неделю. Правки второго класса нельзя делать без
теста, который меняет вход и проверяет, что вывод изменился; и нельзя делать
две сразу.

**1. Починить измерение (М1, М2, М4). Возвращает ноль миллисекунд, стоит один
вечер, риск нулевой.** Перенести `FramePhaseClock::start()` в начало `run_frame`,
`finish()` — в конец, поднять `mark_style()` выше блока разрешения картинок, и
снять на планшете строку `[layer-loop]` рядом с `[phase-stats]`. Сегодня четверть
кадра не наблюдается вообще (весь вывод), `other` врёт по построению, а границы
двух фаз из четырёх смещены. Ни один следующий пункт нельзя оценить, пока это не
сделано: если `present` окажется 6 мс, приоритеты меняются целиком и правильный
ответ лежит в §3.5, а не в композиции. Заодно — распечатать
`components.stale_nodes().len()` при бездействии: если петля крутится вхолостую
(`frame_pipeline.rs:314-318` просит следующий кадр по `has_stale()`), всё
остальное второстепенно.

**2. Безопасная механика композиции (К2, К6б, К7, К8). Возвращает, по оценке,
десятые доли миллисекунды каждая, но их пять, и ни одна не рискованна.** Один
`computed.get(&node)` и один `boxes.get(&node)` на итерацию цикла с передачей
`&ComputedStyle` в хелперы; `shape_paragraph_shared` вместо `.to_vec()` у
одиннадцати вызывающих; четыре ширины рамки читать один раз; `with_capacity` для
`ordered` и восьми хеш-контейнеров; `SmallVec` для `PaintUnit.commands`. Всё это
— локальные правки без состояния, проверяемые существующими тестами на
равенство display list. Ставится сразу после пункта 1, чтобы увидеть, сдвинулась
ли композиция вообще, — и это косвенно проверяет гипотезу «дорог не объём
работы, а промахи кеша».

**3. Индекс правил в `StyleMatcher` плюс идентичность `Stylesheet` (С1, С4, Д1).
Крупнейшая единичная статья фазы стиля; риск средний и управляемый.** Корзины
`класс → правила` строятся один раз на набор листов (там же, где сейчас
`cascade`), `source_order` сохраняется хранением глобального индекса правила,
а корректность проверяется тем, что `ResolvedDeclarations` на каждом узле обязан
совпасть байт в байт со старым путём — это чистая функция, для неё легко
написать сравнительный тест. Отдельной строкой в том же заходе: `if specificity.is_none()`
перед внутренним циклом, и `VersionStamp` вместо `last.sheets != sheets` — вторая
правка снимает и глубокое сравнение в фазе style, и повод для трёх клонов набора.
Здесь уже есть чем ошибиться (порядок каскада), поэтому — отдельным заходом от
пункта 2.

**Дальше, в порядке убывания отношения:** (4) кеш вёрстки абзаца К1 — крупнейший
подозреваемый в композиции, но это первая правка ОПАСНОГО класса, и делать её
надо после того, как пункт 1 подтвердит, что композиция действительно там, где
её ищут; (5) `LoadOp::Clear` В2 — правка в один символ, проверяется числом
`present`, но проверять её можно только после пункта 1; (6) флаги «нет
позиционированных узлов» и «нет scroll-контейнеров» К4/К8 — тоже опасный класс,
зато оба флага фаза стиля выставляет бесплатно; (7) `Rc<InheritedRow>` и
статическая таблица `INITIAL` в резолвере С2 — самая большая правка в списке,
трогает семантику наследования, беритесь последней.

**Чего делать не надо.** Не оптимизируйте реконсилятор (Д2–Д4): его цена меньше,
чем ему приписано (М3), и вся она — сотни `malloc` в фазе на 2.11 мс, из которых
половина принадлежит сборке вида и клону UA-листа. Не трогайте фазу раскладки:
0.9 мс — это 6% кадра, и даже полное устранение двойной раскладки (Р2) даёт доли
миллисекунды. Не переписывайте `obscur-css`: единственная его функция,
исполняемая в кадре, — `CustomValueParser::parse` через `Rc<dyn>` из
`css_pipeline.rs:154`, всё остальное — install-time.

## 5. Что выстрелит потом

Ни одна из этих находок сегодня не стоит ничего. Все они станут дорогими на
сцене, которая у этого приложения впереди, — и все они дешевле чинятся сейчас,
чем после того, как выстрелят.

**Т1. Инкрементальная раскладка не включается НИКОГДА, и на большой сцене это
разница между единицами и десятками миллисекунд.**
`kit/.../runtime/layout_classifier.rs:66`: `classify()` второй строкой делает
`if reconciled || first_frame { return LayoutPhase::Full; }`. На реактивном пути
каждый кадр — `UiCommit`, и любой перерисовавшийся компонент даёт
`reconciled=true` (`reconcile_phase.rs:150`), значит `LayoutPhase::Invalidated` —
весь аппарат `LayoutInvalidation`, `MeasureCache` и `ArrangeCache` — не
включается ни разу: каждое нажатие перекладывает всё дерево целиком, а
`layout_coordinator.rs:215-221` на `Full` чистит оба кеша. На клавиатуре это
стоит 0.9 мс и потому не горит; на сцене с тысячей узлов и текстом весь
инкрементальный код будет мёртвым точно так же. `reconcile_phase` уже возвращает
`roots` — точные корни изменённого; `reconciled` с непустыми корнями должен
давать `Invalidated`, а не `Full`. (Эта находка не проходила состязательной
проверки.)

**Т2. Структурные селекторы дают O(N²) аллокаций на контейнер за кадр.**
`kit/.../orchestration/tree_element.rs:64`: `element_siblings()` фильтрует детей
родителя и `collect()`-ит в новый `Vec`; `index_among_siblings`, `sibling_count` и
`previous_sibling_element` зовут его независимо, а `:last-child` — дважды на одну
проверку. Сейчас молчит: в CSS клавиатуры нет ни `:first-child`, ни `:nth-child`,
ни `+`/`~` (проверено grep). Выстрелит на первой же зебре в списке или на
`:nth-child(even)` в таблице.

**Т3. Виджеты `Table`/`List`/`Tree` материализуют каждую строку без
виртуализации.** `kit/crates/components/obscur-widgets/src/table/table.rs:199`,
`tree.rs:187`, `list.rs:150` — `ViewNode` на каждую ячейку с `cell.clone()`
(`String`). Ни один не пользуется `ViewNode::virtual_list`, которое в
`obscur-view` для этого и заведено. Клавиатура не регистрирует ни одного виджета,
так что сегодня это ноль; тысяча строк — это тысячи `ViewNode` и тысячи клонов
`String` за кадр на сборке вида и столько же узлов на дифе.

**Т4. Текст на меняющейся строке: часы, счётчик, поле ввода.** Три механизма
сходятся в одной точке. `kit/crates/adapters/obscur-text-harfrust/src/shaper.rs:92`
— `shape()` на КАЖДЫЙ вызов делает `FontRef::new` + `ShaperData::new` +
`.build()`, то есть разбирает GSUB/GPOS/GDEF заново на строку (в HarfBuzz это
строится один раз на шрифт). `caching_shaper.rs:90` при переполнении вычищает
кеш ЦЕЛИКОМ (`cache.clear()` при `MAX_ENTRIES = 1024`), а не вытесняет по
использованию — обрыв, а не деградация. `registry.rs:308` — `covers(text)`
парсит шрифт и cmap заново при каждом вызове, а `resolve` зовёт его в
`.filter()` для каждого зарегистрированного лица. Всё три лежат на пути ПРОМАХА
шейп-кеша, поэтому на статичной клавиатуре молчат; строка, меняющаяся каждый
кадр, промахивается по определению.

**Т5. `opacity`-анимация панели даст полноэкранный смешивающий слой на каждый
анимируемый узел.** `kit/crates/adapters/obscur-render-vello/src/conversion/scene_converter.rs:370`
→ `clip_converter.rs:40-48`: `push_layer` для слоя без клипа строит `KurboRect`
со сторонами ±1e9 заново на каждый вызов, а в vello `push_layer` — это клип-слой,
чей bbox отсекается по таргету. Сегодня не стреляет: в листах клавиатуры нет ни
`opacity`, ни `mix-blend-mode`. Выстрелит ровно на анимации появления/убирания
панели и на модалке настроек с затемнением. `subtree_brackets.rs:297` уже умеет
класть реальный bbox — для слоя без клипа его надо протянуть отдельным полем.

**Т6. Прокрутка: `scroll_containers` на каждое событие указателя плюс
квадратичность по глубине.** `scroll.rs:50-77` — внутри уже идущего DFS каждый
узел с `establishes_scroll_container` запускает ВТОРОЙ DFS по своему поддереву;
вложенные контейнеры дают квадратичное поведение. `scroll_targets.rs:39/54/66`
и `pointer_landing.rs:230` зовут полный обход дерева на каждый отчёт указателя.
`settings.css:57` и `palette.css:71` уже объявляют `overflow: hidden`, и
`establishes_scroll_container` считает их контейнерами — то есть выстрелит на
первом же открытии настроек или палитры.

**Т7. Hit-test не пространственный.**
`kit/crates/domain/obscur-interaction/src/spatial/spatial_index.rs:88` — `hits_at`
обходит `BTreeMap` целиком, фильтрует по `contains`, собирает `Vec` и сортирует;
индекс упорядочен по `NodeId`, а не по геометрии, никакого дерева или сетки нет,
только имя. Сверху `hit_testing.rs:128-130` на КАЖДОМ вызове заново строит
`preorder_index` (полный DFS + свежая карта) и `effective_stacking` (второй DFS +
три карты). Сегодня событий в замере нет вовсе; на потоке `pointermove` по
большой сцене это набирается.

**Т8. Grid и flex на длинных списках.**
`grid_item_placement.rs:174` — сетка занятости `Vec<Vec<bool>>`, `mark_block`
проходит по ВСЕМ существующим строкам на каждом размещённом элементе
(O(элементы × ряды)), `first_row` и `first_fit` ищут с нуля для каждого; на
нескольких тысячах элементов это миллионы итераций, и всё пересчитывается с нуля
на КАЖДОЙ мере и КАЖДОМ arrange (`PlacedItems::resolve` без кеша).
`intrinsic_inline.rs:48` — `fit-content` делает два полных зонда по всем детям
(при 0 и при ∞), ни один не попадёт в кеш другого. `flex_layout.rs:498` —
многострочный flex с не-дефолтным `align-content` расставляет каждую линию
дважды.

**Т9. Карты, растущие без вытеснения.**
`kit/.../compiler/custom_value.rs:52` — `CustomValueCache` без верхней границы и
без вытеснения: сегодня множество текстов задано листами и конечно, но
style-атрибут — пятая позиция каскада, и приложение, пишущее
`style="--x: 12.34px"` с меняющимся каждый кадр значением, добавляет по записи на
кадр навсегда. `layout_eviction.rs:70` — множество вытеснения покрывает грязные
узлы, их предков и ПРЯМЫХ детей, но не внуков: если грязный предок изменил
размер, у внуков новый `MeasureKey`, а старая запись не удаляется.

**Т10. `@media`/`@container` вычисляются на каждый узел на каждое правило.**
`stylesheet_compiler.rs:365`: лоуеринг условия сделан правильно, один раз при
компиляции, но `RuleCondition::holds(environment)` зовётся заново для каждого
узла на каждое условное правило (`style_matching_coordinator.rs:149-151`), а
`MediaEnvironment` за кадр не меняется. В CSS клавиатуры нет ни одного `@media`;
на адаптивном листе это тысячи обходов дерева условий за кадр ради одного и того
же ответа.

## 6. Проверено и оказалось невиновным

Не открывайте это заново.

**Опровергнуто состязательной проверкой (было заявлено как находка, оказалось
неверно):**

*Кадр, «пропускающий стиль», клонирует всю карту вычисленных стилей*
(`style_phase.rs:113`) — ветка `!restyle` для этого приложения недостижима:
продуктовая петля жёстко ставит `FrameReason::UiCommit` (`frame_entry.rs:66-73`)
→ `TreeChanged` → `needs_restyle() == true`. Единственные источники
`FrameReason::TextEdit` — собственная сессия редактирования рантайма, а
редактируемого поля у клавиатуры нет вовсе.

*`parse_component` клонирует вид токена; `ValueParser` не переиспользует буферы*
(`value_parser.rs:112`, `:56`) — код такой, как описан, но он не на кадровом
пути: `ValueParser::parse` достижим только из компиляции листа и из
`lower_custom_value`, а последний зовётся исключительно на ПРОМАХЕ
`CustomValueCache`, то есть один раз на пару (свойство, текст) за жизнь процесса.
Заявленные «930 разборов за рестайл» не существуют.

*`CachingShaper`: попадание в кеш стоит четырёх аллокаций и SipHash*
(`caching_shaper.rs:24`) — описание точное, частота неверная: уровнем выше стоит
`ShapeCache`, и `shape_paragraph_shared` при попадании возвращает
`Arc<[ShapedRun]>`, не доходя ни до итемизации, ни до резолвера, ни до
`shaper.shape()` (`paragraph_shaper.rs:149-160`). `CachingShaper` достигается
только на промахе абзацного кеша.

*`ANIMATION_STEP_MS = 16` — такт кадра* (`layer_runner.rs:29`) — нет. Кит просит
настоящий `wl_surface.frame` (`layer_runner.rs:364` → `layer_window.rs:200` →
`layer_state.rs:160`), ворота `:225`/`:232` закрыты, пока композитор не ответил,
`:157-161` — лишь верхняя граница сна в `dispatch` (поток-акквайрер звонит в
waker и заканчивает ожидание досрочно), а `:384-388` — дедлайн ТОЛЬКО до первого
колбэка: дальше запасник переключается на `STALLED_FRAME_MS = 100`. Что
выживает — только дефект наблюдаемости: `refresh_nanos` приходит с каждой
презентации и используется ровно в одном `println!` (`layer_runner.rs:422`), а
`ask_when_shown` зовётся только под `if timed`, то есть в проде обратная связь
презентации не запрашивается вовсе.

*Оффскрин-проход существует ради премультипликации* (`vello_renderer.rs:204`) —
мотив назван неверно: vello рисует вычислительным конвейером в storage-текстуру,
а swapchain-изображение storage-биндингом быть не может; оффскрин плюс блит —
архитектура самого vello, а не цена премультипликации. Убрать проход нельзя,
можно только не платить за него на неизменившихся пикселях (В1).

*Рост набора `COMPUTED_PROPERTIES` объясняет удорожание композиции* — опровергнуто
историей: было 103 записи, стало 101; `PropertyValue` прибавил один вариант в 16
байт; custom-свойства из копии в каждом узле стали общими через `Rc`. Карта узла
стала меньше. Заодно опровергнута посылка «композиция не менялась ни на байт»:
`git diff b791b971 HEAD` по `scene_coordinator.rs` — 233 добавления / 235
удалений, и в сторону удешевления.

**Проверено и работает как задумано:**

`obscur-identity::FastHasher` — ротация, xor, умножение, финализатор; для
`u8`/`u32`-ключей единицы наносекунд; для fieldless enum вроде `PropertyId`
производный `Hash` компилируется в три инструкции. Подтверждён тремя
независимыми проходами как выигрыш. Единственные исключения, оставшиеся на
стандартном SipHash: `MeasureCache.entries` (`measure_cache.rs:12`),
`CachingShaper::cache`, `referenced` в `mark_image_visibility`,
`key_index` в `child_matcher.rs:43` и `SignalGenerations.versions` — все пять
чинятся одной строкой каждая.

`ComposePhase::scaled_root` (`compose_phase.rs:145-158`) перемещает команды, а не
копирует, и на это есть тест с проверкой указателя. `Scene::set_root` — одна
`Arc::new`, `snapshot()` — бамп счётчика (дорога только `SceneStatistics` в
конструкторе, см. В4). `MotionDriver::apply_presentation` больше не клонирует
карту стилей; `drive_css` выходит по `css_motion.is_empty()` (в CSS клавиатуры
нет ни `transition`, ни `@keyframes`). `InlineStyles::apply_all`,
`CanvasPainters::paint`, `VirtualLists::dump_geometry`, `TreeInspector::apply_overlay`,
`ScrollOffsets::refold` — у всех честные ранние выходы, и все они на этой сцене
не исполняются.

Кеш шейпинга работает: `ShapeCache` держит 512 записей в двух поколениях против
~62 различных надписей, тряски поколений нет, промахов на статичной раскладке
нет; `shape_paragraph_uncached`, итемизаторы и `HarfrustShaper` в установившемся
кадре не исполняются вовсе. `StylesheetCache` работает: листы компилируются один
раз при старте и второй раз при смене скина, в кадре ни один лист не
перекомпилируется.

Реконсиляция не проваливается в компоненты (`reconciler.rs:184-186`), при
неизменных пропсах `apply_props` возвращает `false` и ни одна `Key::render` за
кадр не вызывается. Подписки компонентов не накапливаются
(`mounted_component.rs:204` чистит scope перед каждым рендером).
`RetainedTree::get`/`contains` — индексация слот-массива с проверкой поколения,
не хеш. `FrameScheduler` — чистая очередь причин, холостых кадров петля не
гонит. `FramePlan`/`InvalidationRouter` — четыре флага и `match`.

Замков на пути кадра нет: grep по `Mutex`/`RwLock` по `obscur-runtime`,
`obscur-style`, `obscur-scene`, `obscur-text`, `obscur-layout`, `obscur-tree`
даёт ноль; всё разделяемое внутри кадра — `Rc`/`RefCell`. `debug_assert` и
валидация в release выключены (оба воркспейса, `lto = "thin"`,
`codegen-units = 1`, без `debug-assertions`); `DisplayList::is_balanced()` в
боевом коде за кадр не зовётся; шаблон «форматируем, потом решаем, нужно ли» не
встречается ни разу (единственный `format!` на пофреймовом пути —
`virtual_lists.rs:269`, и он за проверкой env). Профиль сборки не виноват:
клавиатура объявляет свой `[profile.release]`, `.cargo/config.toml` ставит
`target-cpu=cortex-a77`.

Swapchain не пересоздаётся на установившемся кадре (`surface_acquirer.rs:110-118`
отбивает повтор того же экстента явным гардом), оффскрин-текстура кешируется,
`vello::Scene` переиспользуется через `reset()`, блиттер и его пайплайн
кешируются по формату, MSAA-семейства не компилируются (`AaSupport::area_only()`),
многопроходная компоновка гейтится на `backdrop-filter`, которого в CSS
клавиатуры нет.

Проценты и `height: 100%` лишних проходов раскладки не требуют (базис протянут
отдельным полем `percent_basis`); flex в форме, в которой его использует
клавиатура, не мерит детей вообще; `ArrangeCache` и `MeasureCache` устроены
разумно — проблема не в них, а в том, что ключи меры между фазами объективно
разные (Р2) и что на кадре с reconcile всё обнуляется (Т1). Три четверти
алгоритмов `obscur-layout` (`DockingLayout`, `ConstraintLayout`,
`PositionedLayout`, `CustomLayout`, весь модуль `observer/`) на кадровом пути не
исполняются вовсе — мёртвый вес в строках, не в микросекундах.

## 7. Чего мы не знаем

**Ни одна цифра в этом документе не измерена.** Всё — чтение кода, grep и
`git log`. Счёт вызовов («33 поиска стиля на узел», «134 правила × 200 узлов»,
«три клона набора листов») прослежен по коду, и на него можно опираться.
Распределение 15.6 мс между находками — нет.

**1. Сколько стоит `present`.** Самый дорогой пробел. Весь §3.5 лежит за
границей измерения, и пока `[layer-loop]` не снят, неизвестно даже, CPU у нас
упирается или GPU. Стоимость проверки: ноль строк кода, один запуск с
`OBSCUR_FRAME_STATS`.

**2. Каким путём идёт типовой кадр — полным рестайлем или инкрементальным.** Это
решающий множитель для всей §3.2: находки С1–С6 умножаются на число
ПЕРЕсопоставленных узлов, а не на 200. Ответ уже пишется в телеметрию —
`phase_clock.record_style_scope(resolved, nodes)` (`style_phase.rs:213`), строка
`styled X/Y nodes`. Никто её не читал. Смежное: `RestyleScope::expand`
(`invalidation/restyle_scope.rs:33`) метит грязным поддерево узла ПЛЮС поддеревья
всех последующих сиблингов безусловно, не спрашивая, есть ли в листах хоть один
комбинатор `+`/`~` (в листах клавиатуры их нет) — если типовой кадр приходит
через `:active` на клавише в ряду, это раздувает грязное множество до конца ряда
без всякой причины.

**3. Сколько узлов в дереве на самом деле.** Оценки колеблются между 190 и 400
(«62 клавиши × ~4 узла вывода компонента плюс оболочка»); цифра 227 взята из
`app/docs/spec-and-perf-audit.md:35`, а не наблюдалась. Все находки «на узел»
линейно масштабируются от неё. Проверяется той же строкой телеметрии.

**4. `size_of::<ComputedValue>()` и `size_of::<LayoutStyle>()`.** Оценки 48–56 и
~200 байт сложены руками по определениям вариантов. На них держится вся
арифметика «8 КБ на узел / 1.8 МБ рабочего набора» (С3) и, через неё, гипотеза
«compose дорог из-за промахов кеша» (К2). Проверяется одной строкой
`println!` в тесте `obscur-style` — дешевле любой другой проверки в списке.

**5. Длина display list.** Ни разу не наблюдалась. Именно она отделила бы
«compose дорог на узел» от «compose дорог на команду», и `SceneStatistics`
(`scene_statistics.rs`) уже умеет отвечать на этот вопрос — телеметрия его
считает и выбрасывает.

**6. От какого коммита собран «августовский» бинарник.** Без этого К3 остаётся
гипотезой: `a789fa0e` и весь окружающий пласт датированы одним днём, история
кита — один сплющенный коммит, у репозитория клавиатуры на master коммитов нет
вовсе. Проверяется не историей, а экспериментом: `--k-radius: 0` в теме (§3.4 К3).

**7. Что происходит ниже display list.** 62 вложенных слоя клипа со скруглением
и 62 гауссовых блюра теней уходят в vello и на Turnip. Стоимость этого не
оценивал никто, и если compose честно стоит, скажем, 3 мс, остальное почти
наверняка там. Внутренности vello 0.9 и wgpu 29 не читались (их исходников в
дереве нет), внутренности Mesa `wsi_wl` — тоже; утверждение, что поток захвата
диспетчеризует нашу же `wl_display`-связь и потому задерживает ввод, помечено
догадкой и не подтверждено ни трассой, ни замером.

**8. Стоит ли у клавиатуры accessibility bridge.** Если да,
`publish_accessibility` (`frame_pipeline.rs:327`) строит `SemanticSnapshot` через
`semantic_builder.rs` (913 строк) на каждом кадре с `reconciled`, целиком вне
замера фаз. Это потенциально крупная находка, которую никто не смог
подтвердить: нужно посмотреть, зовёт ли приложение `set_accessibility_bridge`.

**9. Не крутится ли петля вхолостую.** `self.components.has_stale()` в конце
`run_frame` (`frame_pipeline.rs:314-318`) запрашивает следующий `UiCommit`-кадр.
Если компонент помечает себя устаревшим внутри собственного `render`, это
самоподдерживающийся поток кадров на 120 Гц при нулевом вводе — и тогда всё
остальное в этом документе второстепенно. Проверяется одной печатью
`stale_nodes().len()` при бездействии.

**10. Сколько узлов идут компонентно-скоупленным путём.**
`style_matching_coordinator.rs:200` (`scoped_internal_declarations`) держит свою
копию того же перебора всех правил, плюс вызов `subject_part_name` и
`part_specificity_for` на каждый селектор каждого правила. Если клавиши —
компонентные внутренности, горячая функция именно эта, а не `match_element_in`;
выставлен ли на них `OPEN_STYLE_SCOPE`, никто не установил.

**11. `dispatch_queued_input` и путь события указателя целиком.** Прочитан только
верхний уровень (`queued_input.rs:17-38`); сам разбор уходит в
`hit_testing.rs` (1058 строк). Известно лишь, что он лежит ВНЕ измеряемого
промежутка часов фаз и потому кандидат на непокрытые миллисекунды. Сколько раз за
одно касание зовётся `HitTesting::resolve` — на каждый сэмпл движения или только
на down/up — не выяснено, а от этого зависит класс Т7.
