## Why this audit exists

The previous audit called §5 "genuinely wired end-to-end" with "none" Tier-1, and recorded the "built but not wired" theme as "largely closed". Both are false, and the *reason* they are false is the finding that matters most:

> **A type existing is not evidence that anything calls it — and a doc comment asserting the wiring is how a reviewer gets convinced otherwise.**

Three doc comments in this codebase assert an architecture that is not connected:

- `child_measurer.rs:19` — leaves "route to the intrinsic-measure port `IntrinsicMeasure`". They do not; `IntrinsicMeasure` has no production consumer.
- ~~`layout_invalidation.rs:12` — "the structured replacement for scattered ad-hoc dirty flags". The shipped model *is* four booleans.~~ **Rewritten by the 3-A fix.** `layout_invalidation.rs:12` now heads a *Status: the layout phase does not consume this* section naming `layout_is_needed` as the caller that fills the accumulator and reads nothing off it. The finding it recorded is still true of layout; the doc no longer asserts otherwise. Two of the three remain.
- `frame_budget.rs:15` — "the emitted `Diagnostic` flows through the normal diagnostics channel". Nothing emits, and there is no channel.

This audit therefore treats **"who calls it?"** as the primary question, and reports a doc that describes an unbuilt mechanism as a finding in its own right.

### The dominant pattern

**The domain crates are richer than the runtime that consumes them.** Roughly a third of `obscur-layout`, all of `obscur-system`, all of `obscur-routing`, all of `obscur-windowing`, the whole diagnostics subscription tier, the whole record/replay tier, and — until 5-C put the §5.19 policy tier on the runtime's decoded-image cache — every §5.19 cache compile, pass tests, and are called by nothing. The three Vello caches, `StyleCache` and `LayoutCache` still are.

The structural cause is visible in one file: **`crates/facade/obscur-kit/src/lib.rs` is a re-export barrel** (lines 30–105 are `pub use X as y;` and nothing else). Anything whose only path to the outside is that file is unwired by construction. That is what hid `obscur-data-transfer` from the last audit; it now accounts for `obscur-system` and `obscur-routing` wholesale.

## Tier-1 findings

### §1 — the dynamic architecture has no execution path

**1-A. A component render failure keeps stale UI and is reported on no channel.** — **fixed for component renders.**
Was: `let Ok(view) = mounted.render(..) else { errors += 1; continue; }`, and that `continue` was the whole of §1.7. Now `MountedComponent` owns an `ErrorBoundary` built from the author's `error_boundary()` and a new `Component::fallback()`, and `render` returns `GuardedRender` — the boundary's decision, taken via `ComponentRecovery`, never a raw `Result`. `render_components` enacts it: a retry leaves the subtree and schedules the frame that spends the budget, an exhausted budget commits the fallback *over* the subtree, and a disabled boundary propagates to the nearest enclosing enabled one, whose subtree is replaced instead. `ErrorBoundaryPolicy::disabled()` now differs from enabled on every axis.

Still open, and deliberately: two paths still leave the last output standing. A **retry** does for the frames the budget buys (that is what a retry *is*), and a **propagated failure with no enclosing enabled boundary** does indefinitely — every boundary that could have answered was disabled. Both are reported; neither is silent. `SubsystemRecovery` remains uncalled, so §1.7's "layout, renderer and resource failures use subsystem-specific recovery boundaries" is still unbuilt.

**1-B. No production code in this workspace ever constructs a `Diagnostic`.** — **fixed; two producers now, one of them delivered.**
`MountedComponent::contain` builds one (via `ComponentFailure`) under a stable `view.component.props` code, and `UiRuntime::report_failure` (`ui_runtime.rs:1687`) stamps the two §1.6 fields only the runtime knows — the node it concerns and the `RecoveryAction` actually taken — before emitting to a `DiagnosticSink` installed by `set_diagnostic_sink` (`ui_runtime.rs:1758`). A test drives it through the shipped `ChannelSink`/`DiagnosticChannel` to a filtered subscriber (`ui_runtime.rs:6719`), so the §7.8 subscription path is exercised end-to-end rather than asserted. The default is a `NullDiagnosticSink`, so the failure path does not branch on whether anyone listens.

The second producer arrived with 5-A and is **built but not delivered**. `EffectFallbackReporter::report`/`report_fallbacks` (`effect_report.rs:239`, `:275`) construct real `Diagnostic`s under `render.effect.unsupported` / `render.effect.fallback`, and both backends call them from `Renderer::render` itself — `cpu_renderer.rs:328`/`:334` and `vello_renderer.rs:246`/`:254`, all far above their crates' `#[cfg(test)]` gates (1327 and 1014). This is not a theoretical path: the CPU backend's `supports_effect` (`cpu_renderer.rs:605-617`) declares `Gradient`, `Blur`, `Mask`, `BlendMode`, `BackdropFilter` and `ColorMatrix` `Unavailable`, so an ordinary gradient raises one on its first frame. But **nothing installs the sink**: `set_diagnostic_sink` on either backend (`cpu_renderer.rs:194`, `vello_renderer.rs:122`) has zero callers outside those crates' own tests, the default is a `NullDiagnosticSink` (`cpu_renderer.rs:164`, `vello_renderer.rs:96`), and the `Renderer` port carries no sink — four methods (`renderer.rs:44-91`), none an installer — so `UiRuntime` cannot install one even in principle. Every §5.2 render diagnostic is therefore built and dropped. The backend's own doc (`cpu_renderer.rs:187-193`) says exactly this, which is the honest version of the failure this audit exists to catch.

The runtime's sink still carries **only** component-render failures. Every other subsystem reports through its own path (a `BudgetViolation`, a `Result`, a last-good value); routing those through the sink is separate work.

**1-C. The kit cannot create a window (§1.4 R8).** — **CLOSED in f5ebdb8: the kit opens a window through its own port, and presents real GPU frames through it.**
Was: `WinitWindowBackend` had **zero consumers** and grew from 526 to 934 lines during this campaign without acquiring one, while six examples each called winit's `event_loop.create_window` directly. The verdict on inspection was that the port is *not* misshapen and deferred creation is *not* the blocker — it composes fine and nobody had tried. It needed one addition: `WinitWindowBackend::native_window(id) -> Option<Arc<winit::window::Window>>`, because `create_window` returns an id and wgpu needs the handle. That sits on the **adapter**, not the port — §1.1 forbids winit types leaking into the pure domain, and the host already names winit because it owns the event loop. `windowed_counter.rs` now creates through `WindowBackend::create_window` with domain `WindowProperties`, fetches the handle, and presents Vello frames; proven by a real run, and by an attended `#[ignore]`d two-window test that pins handle *identity* (a `native_window` ignoring its argument fails it).

**The audit's implied remedy was wrong, and is withdrawn.** This entry led with "`obscur-runtime` does not depend on `obscur-windowing`" as if that edge were the fix. It is not: §1.4 requires the runtime to run "headless mode without windows or GPU" and "embedded mode inside an existing host window", and §1.3 forbids linking unused backends — a runtime→windowing edge would link a window model into every headless app. **The composition point is the host**, and the missing piece was a reachable handle, not a dependency. The observation was true; the inference from it was not.

**Still open:** (a) five of six examples still hand-wire — `capabilities_window`, `controls_window`, `showcase_window`, `uikit_window`, `wireframe_live_window` — though all five need the identical trio the converted one now gets through the port; (b) **§1.4 R10 overlay mode has no representation at all** (zero hits for `overlay` in `obscur-windowing`; zero for `OverlayMode`/`OverlayHost`/`WindowKind::Overlay` repo-wide) — and adding an unconsumed enum variant would be this audit's own defect; (c) **a new silent wrongness the wiring exposed**: `WindowEvent::Resized` passes winit's **physical** pixels through while creation uses **logical** (`with_inner_size(LogicalSize::new(..))`). Both are domain `Size`, so the type system flags nothing — ask for 480×240, read back 960×480 at 2×. `windowed_counter` is correct today only because this display is scale 1. Documented and deliberately **not** pinned by a test: asserting the current behaviour would be asserting the bug.

### §2 — the primary authoring surface is unchecked

**2-A. §2.13 is unenforced where it matters.** — **PARTIALLY CLOSED: the macro enforces now. The other two gaps are narrower than the entry says, and one of them is structural.**

Was: three compounding gaps: the `okui!` macro — self-declared "the spec's *primary* authoring surface" — runs **no** contract validation; the `.okui` path skips any tag with no registered contract; and `register_surface` is called only from a test, so no user component's contract can be checked. "Unknown attributes… are compile errors" holds only for the 20 hard-coded built-in tags, and only on the file path.

Now: `okui! { <Button laebl="OK"/> }` is a compile error at the author's own token, as are an undeclared `on:` event, an omitted required prop, and every §2.12 slot rule. The root was not the rule but *where it was written*: `ContractValidator::validate_element` took an `obscur_okui_syntax::ast::Element`, which this front end does not have and never will (it parses `TokenStream`s with `syn`). The rule now lives over plain data in `validation::contract_rule::check_contract`, and each front end is a thin adapter that describes its own instance and resolves a `ViolationAnchor` to its own kind of location — a byte offset for the file, a `Span` for the macro. That is the shape `check_expression` already gave §2.10. Two `okui!` documents in this repo's own tests were illegal and are now fixed, which is the check earning its keep.

**Still open, and the third gap is a wall rather than a wire:**

- **A proc-macro cannot see a user component's contract. Ever.** The macro checks `ContractRegistry::builtins()` — the primitives and widgets, whose surfaces are compiled into it. `MyProps::contract_surface()` is a function that runs when the *built crate* runs; the macro ran while that crate was being compiled. The file front end takes its registry as an argument and so can be handed one; a macro has no argument to take it in. This is why the `.okui` path is not simply the redundant fallback the docs imply.
- **`register_surface` still has no in-repo caller** outside tests, so on the file path too, a user component is checked only if a build wires it. There is no auto-discovery.
- **The "skips any tag with no registered contract" gap is worse than unchecked.** `name_binding::component_id_for` resolves every unrecognised tag to `CONTAINER`, so `<Card/>` in either front end is not a mis-checked component — it is a **generic box**. No user component can be authored in `.okui` or `okui!` at all. §2.12's slots and §2.13's contracts are therefore enforced against a tag that lowers to a `div`; the check is real and stops a bad build, but the thing it names cannot yet be instantiated. That is a §2.14 registry gap holding up both.

**2-B. Dynamic text bindings are silently wrong on both front ends.** ~~`okui! { <div>{user.name}</div> }` renders the literal text **`"user.name"`** (`dsl_macro.rs:138`), and a test at `:551` *asserts the bug*. The `.okui` path renders an empty box.~~ **Closed on the codegen path, which is both front ends' production path.** They now build one `UiIrNode::interpolation` carrying the expression, and `ViewCodegen` emits `ViewNode::text(ToString::to_string(&(user.name)))` — the same "a binding is a Rust path" design `d1a11bc` gave attributes. The test that asserted the bug is inverted; `okui_text_binding.rs` proves the value renders, through the real macro with real locals. Two things stay open, neither introduced by that fix:

- `document_to_view_fn` emits a *nullary* `pub fn <name>() -> View`, so a compiled file's bindings can only name what the generated module has around it. A file whose bindings read per-call state does not compile — the function has no parameters to read it from — and giving it them needs a props-signature decision nothing makes yet. This has bounded every `.okui` file binding since `d1a11bc`; text is not special.
- `UiIrViewBridge`, the *interpreter*, still renders an interpolation as an unknown element (an empty box) and still lowers an attribute binding to its path's spelling. It cannot do better by construction — there is no Rust scope to resolve a path in at runtime — and it has no production consumer (tests plus `showcase_okui_png`). A binding is a compile-time construct here; the bridge is the artifact of that.

**2-C. §2.12 is unimplemented below the type layer.** — **PARTIALLY CLOSED: declared, parsed and ENFORCED on both front ends. Not routed, and routing is the part that does not survive contact with the pipeline.**

Was: `ViewNode` does not model slots (one anonymous `children`); `SyntaxKind` has no slot node; `SlotContract`/`SlotCardinality`/`StylePartContract` have zero production consumers; `Template::slot_names()` and `SymbolKind::Slot` are dead. Nothing parses, validates or routes a slot.

Now, for the **assignment** — the consumer side of a slot:

- **Declared.** `#[contract(slot(name = "header", cardinality = one, child = "Title"))]` on a props struct emits the slot onto both views `#[derive(Contract)]` already emits: the string `ComponentSurface` (new `SlotSurface`) and the typed `ComponentContract`'s `slots`. `SlotCardinality` is the **same type** on both sides, not a re-spelling, and `SlotCardinality::accepts` is what decides.
- **Enforced.** `slot="…"` must name a declared slot (`unknown slot 'headr' on component 'Card'`), satisfy that slot's own child rule, and the slot's cardinality must hold in both directions. A `slot=` on a component that declares none is a distinct diagnostic, because it is a category error rather than a typo. A `slot={expr}` is refused: a slot is matched against a declaration at compile time. Asserted through the real `Compiler` with a real derived surface, and through the real `okui!` macro (`crates/facade/obscur-kit/tests/okui_slots.rs`, `dsl_macro.rs`'s own tests).
- **The rule looks through control flow**, because `<If>`/`<For>` splice their bodies into the enclosing child list — so `<Card><For …><p slot="bdy"/></For></Card>` is Card's member and its typo is caught. What that costs is carried honestly: a member behind an `<If>` may be absent and a member in a `<For>` may repeat, so cardinality reports only what is wrong for **every** count the bound admits. A conditional member is never accused.
- **The rule moved out of the AST** (`validation::contract_rule`) so both front ends reach it — which is what let 2-A's first gap close (below).

**Not built, and each for a reason rather than a TODO:**

- **Nothing routes a slot, and there is nowhere to route it to.** A slot system projects content into a template; this pipeline has no template. `Component::render(&mut self, ctx, props) -> View` takes **props only** — a component never receives children — and codegen emits a component tag as `ViewNode::element(COMPONENT_ID)`, a node kind, not a call of anything. So there is no "where the slot is" for content to move to. Declaration order is the only candidate destination, and §2.12 does not say order means anything; inventing that is what `5e8e7fe` refused for `<Loading>`. **A slot assignment is therefore a compile-time construct**, like a binding being a Rust path.
- **`ViewNode` still does not model slots** — deliberately, and this is the same finding as the line above. A `slot` field on `ViewNode` would be written by codegen and read by nobody: no component consumes children, and `TreeElement::attribute` resolves only `id`/`type`, so not even CSS could see it. The assignment reaches the tree as an ordinary property, which is what it already did; `a_slot_assignment_is_not_a_prop_the_tree_carries` pins that.
- **`SyntaxKind` still has no slot node.** A slot node would be the *placeholder* (`<slot name="header"/>`) — the template side, which does not exist. The assignment is an attribute, which the parser already has; `Template`'s own model always said so.
- **No shipped component declares a slot.** `Dialog` is the only widget that takes authored children and its model is one anonymous list; giving it named regions would be inventing a surface, not mirroring one (the same rule `builtin_contracts` already follows for `<Tab>`/`<Column>`). So the *only* subject of the check today is a user component with a registered surface — see 2-A.
- **`Template::slot_names()`, `SymbolKind::Slot` and `StylePartContract` are still dead.** `slot_names` had its docs corrected: it collects *assignments*, not the declarations its name implies, and the type it hangs off is unreachable (the parser never emits a `Template` node). §2.12's "exported style parts / visual states" is untouched: `StylePartContract` appears only in its own file and as an unread `ComponentContract` field, and nothing could consume one — the selector compiler *does* lower a pseudo-element through (`selector_compiler.rs:155`), but `selector_matcher.rs:136` answers **false** for every one that reaches it (4-C's fail-closed fix), so no `::part(…)` can match.
- **The typed `ComponentContract`'s `slots` has no production reader** — as is true of its props and events. It is emitted anyway because a component that declares a slot and reports `slots: []` would be *wrong*; an unread field beats a lying one. The reader that exists is on the string surface.

**2-D. `<VirtualFor>` is `<For>` with a different spelling.** ~~Parsed, classified, lowered with its tag — and `emit_loop` never reads the tag. A tag whose entire purpose is a performance contract, honoured by nothing, with no diagnostic.~~ **Closed as a refusal, not as an implementation — and the distinction is the entry.**

`<VirtualFor>` is now rejected on **both** front ends, the way `float` and `@container` are rejected: `validation::collection_rule::check_collection` is one rule over a plain tag string — the shape `check_expression` and `check_contract` already have, for the same reason (there are two authoring surfaces and only one has a `.okui` syntax tree, which is how the two came to ignore this tag *together*). The `.okui` path reports it as a `ValidationDiagnostic` at the tag's byte offset, and `has_errors()` is what `obscur-kit`'s `build.rs` already panics on — so the verdict is acted on rather than recorded. The `okui!` macro reports a `syn::Error` on the author's own tag. Neutering `check_collection` to `Ok(())` fails four compiler tests and one macro test, and the macro's failure output shows the finding verbatim: `kind: Loop, tag: "VirtualFor"`, accepted and carried to an emitter that never reads it.

**Why refused rather than implemented, on evidence.** §4.9's contract is materialization + overscan + estimated geometry + scroll anchoring, and the mechanism for it already exists and is *complete*: `obscur_layout::virtualization::{VirtualLayout, MaterializedRange, OverscanPolicy, SizeEstimator, ScrollAnchor}`. It has **zero consumers** — `grep` outside its own module returns nothing but `pub mod virtualization;`. It could not have one here: `VirtualLayout::visible_range(scroll_offset, viewport_extent, item_count)` names two inputs a *view builder* does not have (it runs before layout, and is handed neither), `document_to_view_fn` emits a **nullary** `pub fn <name>() -> View` so a compiled file's loop cannot read them from anywhere at all, and estimated geometry and scroll anchoring are retained state across frames that a `for` loop in a view builder does not have. Wiring it needs a retained collection consumer that owns scroll state and rebuilds a window on scroll — a tier of its own, not a codegen change. Inventing a `<VirtualFor scroll={} viewport={} item_extent={}>` attribute surface would be the same move `5e8e7fe` refused for `<Loading>`: the spec names no such attributes.

**Still open:** §4.9 is **unimplemented**, and that is now a refusal with a diagnostic rather than a silent lie. There is no windowed rendering in this kit; `VirtualLayout` and its four companions remain a complete, tested, unconsumed mechanism. `LoopExpression::is_virtual` (`loop_expression.rs:60`) still exists in the syntax crate with no consumer — an AST accessor for a tag that no longer compiles. And the file front end's refusal rides the *accumulating* diagnostic stream, so a caller who reads `document()` without `has_errors()` still gets IR with a `VirtualFor` loop node in it — the same contract §2.10's expression allow-list has, and the reason `build.rs` checks (`ui_ir_lowering.rs`'s own test says so at the point it still lowers one).

### §3 — invalidation is per-node on the style phase, boolean-per-phase everywhere else

**3-A. §3.4 step 8 "incremental layout" does not exist.** — **PARTIALLY CLOSED: the STYLE phase now takes a dirty set. Layout — which is what this entry is named after — still does not.**

Was: every node payload in the chain — `UiOperation::{Rerender,InvalidateStyle,InvalidateLayout}.node`, `Invalidation::node()`, `StyleInvalidation::invalidate(node,…)`, `LayoutInvalidation::invalidate(node,…)` — is **write-only**. No production reader of `is_invalidated`/`reason` exists. Both phase consumers (`StyleCoordinator::resolve`, `LayoutCoordinator::layout_editing`) take no dirty set and walk the whole tree. A hover on one node ⇒ full restyle of every node.

Now, on the interaction path only: `UiRuntime::restyle_scope` builds a `StyleInvalidation` from the nodes whose `PseudoStates` entry changed since the last styled frame; `StyleMatchingCoordinator::rematch_into` iterates it to re-match exactly those elements; `StyleCoordinator::resolve_incremental` reads **`is_invalidated`** per node to decide resolve-or-retain. A hover on a leaf resolves 1 node, not the tree — asserted by counting the runtime's own `style.resolved` telemetry, not by observing that a frame rendered (`crates/facade/obscur-kit/tests/incremental_restyle.rs`).

The scope is **`subtree(N) ∪ ⋃ subtree(S)` over N's following siblings**, which is sound rather than guessed: `MatchElement`'s entire navigation surface is `parent()` + `previous_sibling_element()`, so no matcher can read N's state from anywhere else, and `:has()` — the one selector that would reach upward — lowers to `PseudoClassSelector::Other` (`selector_compiler.rs:211`) which the matcher answers `false` for (`selector_matcher.rs:203`). The set is downward-closed, so inheritance needs no second pass. Neutering the reach to "just the hovered node" makes `.a:hover .leaf` render **blue instead of red** — verified.

**Still open, and none of it is incidental:**

- **Layout is untouched.** `LayoutCoordinator::layout_editing` still takes no dirty set and arranges the whole tree; `layout_is_needed` still only refines the run/skip **boolean**. `LayoutInvalidation` remains **write-only** — populated in `layout_is_needed` and dropped unread. The entry's own title is therefore not closed.
- **`reason` still has no production reader.** `is_invalidated` gained one; `StyleInvalidationReason` is recorded on every node and nothing branches on it (`rematch_into` ignores it). `take`/`drain` have no caller either.
- **The `UiOperation`/`Invalidation` node payloads are still write-only.** The dirty set is derived from the live `PseudoStates` diff, *not* from `Invalidation::node()`. An `InvalidateStyle { node }` still restyles the whole tree.

- **The bound is not narrowed by what the sheets say.** `StyleDependency` — the per-node record of what a node's matching consulted — still has no production consumer, because `match_element_in` returns no dependency trace. Hovering inside a large subtree restyles that subtree even when no rule mentions `:hover`.

- **4-B is not unblocked by this.** No layout-interleaved restyle pass was built, so `@container` still has no resolved size to match against.

§4.3 closes with *"Scattered ad hoc dirty flags are not the architectural model"*; the phase-selection model is still `style_dirty`/`layout_dirty`/`scene_dirty`/`paint_dirty`, now with a per-node set *inside* the style phase. The three docs that asserted the unbuilt architecture (`layout_invalidation.rs:12`, `style_dependency.rs`, `frame_plan.rs`) were rewritten to state which half is real.

**3-B. §3.1 dependency tracking is wired to nothing and defeated downstream.** — **unchanged in verdict; the downstream defeat now runs through a different gate.** `ComponentContext::track` (`component_context.rs:79`) must be called by hand and its only call site is a test (`ui_runtime.rs:6038`, below the `#[cfg(test)]` at `:5904`). `notify_signal` (`:1823`) and `register_component` (`:1777`) have no caller below that gate; all six windowed examples install `set_root_view` (whole-view rebuild) instead. ### §4 — relative units die at the layout↔paint seam

**4-A. `font-size: 2rem` renders at 16px, and poisons every `em` on the node.** — **CLOSED for `em`/`rem`/`vw`/`vh`/`vmin`/`vmax`, and for the one `%` that reached paint (`border-radius`); still open for `ch`.** Was: `ComputedStyle` never absolutized lengths — layout resolved via `resolve_px(ctx)` while paint read the same property through `as_px()` (absolute px only), so `border-width: .1em` **reserved layout space and painted nothing** and the two phases disagreed about the same box.

Now: `computed/absolutize.rs` is the one fold, and `StyleResolver::resolve` runs it over every computed property (`style_resolver.rs:633`) against a `LengthContext` built from the `font-size` resolved one step earlier (`:613-623`) — so paint's `as_px()` reads became *correct* rather than being removed. The match is exhaustive rather than wildcarded, so a new length-bearing `PropertyValue` variant cannot quietly opt out and reintroduce the seam. `tests/relative_units_paint.rs` asserts against the **published `DisplayList`**, never a hand-built scene: `2rem` paints at 32, an `.1em` border paints exactly the 4px edge layout reserved (and the identical edge its `4px` control paints), `box-shadow: 1em .5rem 1vw 2px` lands on offset `(20, 8)` / blur `4`, and `10vw` vs `10vh` read different axes on a deliberately non-square viewport. Neutering the fold fails 6 of its 10 tests.

**`border-radius: 50%` — the circle idiom — is now CLOSED**, and it is the one `%` that ever reached this seam. (`border-*-width` takes no percentage; `font-size: 50%` never had this bug — `absolute_font_size` resolves it against the parent's size via `with_percent_basis`. A `%` on a *layout* property is resolved by layout against its containing block, which is not this seam.)

Was: a `%` is deliberately not absolutized (its basis is the box, which layout has not produced), and `corner_radii_of` read the computed length through `Length::as_px` without the `bounds` it would need, yielding `0` — a square corner. The two things it needed are both built. (1) **A `CornerRadii` that carries two radii per corner**: `CornerRadius { x, y }` (`corner_radii.rs`) makes a corner the *quarter ellipse* CSS Backgrounds 3 §4.1 actually defines, and `Path::rounded_rect` drives each axis from its own radius, so the ellipse survives into the outline. (2) **Percentage resolution in paint**: `corner_radius_of` (`scene_coordinator.rs`) resolves a `Percent` per axis against the arranged border box — §4.1's "percentages for the horizontal radius refer to the width of the border box, whereas percentages for the vertical radius refer to the height" — so `50%` on a 200×100 box is `(100, 50)`, an ellipse, and a circle only when the box is square. Resolution and the §4.5 overlapping-curves correction both run **once**, at the single point the radii are derived, so every consumer (background fill, subtree clip, border ring, shadow, outline) sees the same resolved radii.

`normalized` implements §4.5 verbatim (`f = min(Li/Si)`, one scale applied to *all* corners) rather than the old per-corner `min(w,h)/2` clamp, which is what makes `50%` survive: every side sum equals that side's length exactly, so `f == 1` and the authored ellipse is left alone. Proven by `border_radius_fifty_percent_paints_an_ellipse_on_a_nonsquare_box`, which drives the real `SceneCoordinator` and reads the radii off the emitted path's anchors — a case no scalar radius can express. Neutering the two halves fails them **disjointly**: resolving both axes against the width fails both it and `percent_radius_resolves_per_axis_against_the_border_box`; making the path builder use one axis fails only the paint test. `clip_cross_backend.rs` pins that both backends admit the same points for an elliptical clip (§5.2) — though note its *agreement* assertion cannot catch a defect in the shared `Path::rounded_rect`, which would make both backends wrong together; only its expected values can, and they are chosen to sit where a scalar radius and a true ellipse actually disagree.

**Still open — the seam is closed for the units that fold, not for the one that does not:**

- **`ch` still dies at the seam, exactly as `em` did.** `Length::absolutize` leaves `Ch` symbolic when `ctx.ch_width` is `None` (`length.rs:129`), and the resolver's context never carries one (`style_resolver.rs:618` passes four arguments; `with_ch_width` has no caller there). Only **layout** measures the `0` glyph (`layout_coordinator.rs:745`'s `ch_width_for`). Measured at HEAD: `.box{width:100px;font-size:40px;border-style:solid;border-width:1ch}` arranges a **148px** border box — 24px of `ch` per side — and paints a **0px** edge. The choice is deliberate and documented (folding it here would bake in `ch_base`'s `0.5em` substitute and permanently mis-size the monospace column `ch` exists for), but the layout/paint disagreement this entry names is still live for it.
- **The two backends diverge on blurred effects, by backend limitation, and now say so rather than silently picking an axis.** Clip and scene geometry — what §5.2 requires to match — go through `Path` on both backends and carry the true ellipse. But two Vello paths can only express a *circular* radius. **`box-shadow` on Vello** collapses to one scalar (`blurred_shadow_radius`, `scene_converter.rs`): `vello 0.9`'s `Scene::draw_blurred_rounded_rect` takes a single `f64` radius — no per-corner and no elliptical form (kurbo's `RoundedRectRadii` is four *scalars*, so it does not rescue the elliptical case either). The CPU backend builds its shadow from `Path` and keeps the ellipse; Vello rounds it. **`backdrop-filter` on Vello** likewise: the mask's WGSL SDF (`gaussian_blur.wgsl`'s `rounded_rect_coverage`) is a per-corner *circular* rounded box (`length(q) - r`). Both use `CornerRadius::circular_approximation` — the mean of the two axes, exact whenever the corner is already circular (so the common uniform radius never degrades) and unbiased when not. This follows the CPU/Vello effect-table precedent: a GPU-class effect may approximate, provided the table tells the truth.
- **`box-shadow` spread is missing §6.1.1's easing** — found while closing the above, *not* closed, and strictly speaking not part of 4-A. `CornerRadii::offset` adds the spread distance raw; §6.1.1 first scales it by `1 + (r−1)³` when a radius is smaller than the spread, so a 10px radius with 20px spread should give 27.5px and gives 30px. It is correct at both endpoints (`r == 0` and `r ≥ spread`), which is why no test caught it. The easing must **not** be added to `offset` — §4.2's inner-border radius shares that method and prescribes a plain subtraction with no easing; spread needs its own method. Documented at the definition.

**4-B. `@container` always matches.** — **CLOSED (fails closed + diagnostic); still not implemented.** Was: full parse→lower→evaluate chain exists, but `MediaEnvironment::with_container` has **zero callers** and there is no `container-type` property, so unset ⇒ non-restrictive ⇒ holds — failing open, the worst mode for a gate.

Now: an unknown *container* axis evaluates to **false** (`FeatureQuery::holds`), an unrepresentable container feature lowers to `Never` rather than `Always`, a bare `@container name { … }` lowers to `Never`, and the parser records an `UnsupportedCssFeature(AtRule, "@container")` on `CompiledStylesheet::unsupported`. Viewport axes keep their permissive `unbounded()` opt-out — the asymmetry is deliberate and documented (css-contain-3 §3.1).

Two scoping caveats, or this entry becomes the next over-claim: "inert" covers **matchable declarations**; the motion path (`stylesheet_compiler.rs:404-409`) is a separate lowering. And the diagnostic is **recorded, not reported** — `unsupported` has no production reader (every consumer takes `.matchable`), which is the same decorative-diagnostics finding §5-A records.

**Still open:** `@container` rules are *inert*, not *working*. There is no `container-type`/`container-name` property, and `with_container` still has no production caller. Wiring it for real needs a container's resolved size during matching, but `build_inputs_env` matches the whole tree strictly *before* `style.resolve` and layout, and there is no layout-interleaved restyle pass. §4.13 listing container queries as *Supported* remains an over-claim against the implementation.

**4-C. `::before`/`::after` apply their declarations to the originating element.** — **CLOSED (fails closed + diagnostic); still not implemented.** Was: `selector_matcher.rs:134`: `PseudoElement(_) => true`, so `.badge::before { color: red }` painted `.badge` red — an omission would have failed closed; this did not.

Now: `selector_matcher.rs:136` answers **false** for every pseudo-element, so any compound containing one is inert and no wrong box is painted, and `selector_compiler.rs:292-297` records an `UnsupportedCssFeature(PseudoElement, "::before")` — the same channel `:visited` and `float` use. Neutering the arm back to `true` fails `pseudo_element_never_matches_its_originating_element` (`selector_matcher.rs:429`). The compiler still *lowers* the selector through (`selector_compiler.rs:155`); the matcher is the gate, which is why the lowering surviving is not the leak.

**Still open:** there is no generated box. `PropertyId::Content` does not exist (zero hits across `obscur-style`'s property table), so `::before`/`::after` are diagnosed, not implemented. And the diagnostic is **recorded, not reported** — `CompiledStylesheet::unsupported` has no production reader, the same caveat 4-B carries.

**4-D. Intrinsic sizing is flow-`width`-only.** — **CLOSED for bounds, flex basis and grid tracks; three degradations remain, each named.** Was: `is_intrinsic` had exactly one production caller, so `min-/max-width: min-content` applied **no clamp at all**, flex `flex-basis`/`width: <intrinsic>` degraded to `auto`, and `grid-template-columns: min-content` **dropped the entire track list**.

Now: `is_intrinsic` has three production callers (`size_clamp.rs:84`, `flow_layout.rs:216`, `flow_layout.rs:398`). An intrinsic **bound** is measured and returned as a content extent, with `box-sizing` correctly *not* reinterpreting it (`size_clamp.rs:84`'s `bound_content`). Flex resolves an intrinsic **main-axis** size or `flex-basis` by probing the item rather than falling through into the natural-size fallback (`flex_layout.rs:121-138`'s `intrinsic_main`: `min-content` at a zero offer, `max-content` unbounded, `fit-content` as CSS 2.1 §10.3.5 shrink-to-fit). And `grid_track_scalar` lowers `min-content`/`max-content` (`property_compiler.rs:1857-1862`), so one content keyword no longer takes the `1fr` beside it down with it. `tests/intrinsic_sizing.rs` drives all three end-to-end against arranged boxes derived from the actual text (17 tests); neutering `bound_content`'s intrinsic arm fails its three bound tests disjointly.

**Still open, and named rather than rounded up:**

- **A flex or grid container's own `width`/`height`** still degrades to `auto` — `display: flex; width: min-content` fills its parent — as do **its own `min-`/`max-` bounds**, which impose no clamp: only flow measures its bounds.
- **A flex item's cross-axis size and cross bounds** likewise. Each needs a min-content pass over a formatting context that has none: flow's probe stacks children, which is not what a flex row or a grid does.
- **`fit-content` is still not a grid track.** CSS Grid spells it `fit-content(<length-percentage>)` — a function whose argument is unmodelled — so it stays unrecognised and still degrades the whole declaration (`property_compiler.rs:1847-1850`).

### §5 — font subsystem real but Linux-only; one cache bounded, the rest dead; diagnostics emitted into a null sink

**5-A. §5.2's "explicit diagnostics" requirement is decorative.** — **CLOSED for `Unavailable` effects, and for the one `Limited` fallback both backends share (text); the remaining `Limited` arms are declared, not emitted, and are named below.** `RendererError::UnsupportedEffect` was **never constructed**; `Renderer::supports_effect` had no production consumer. The previous audit converted this into a clean bill of health ("documented policy, correctly reported via `supports_effect`") — nothing read it, and what it reported was wrong: CPU claimed `Emulated` for blur while `DrawShadow` destructures `blur: _` and draws a hard rect. **That is `Unavailable`.**

Now: the effect vocabulary is closed (`SceneEffect`), so each backend's table is an exhaustive match the compiler checks and every arm was re-derived from the paint path. CPU: `Blur`/`BackdropFilter`/`ColorMatrix`/`Gradient`/`Mask`/`BlendMode` → `Unavailable` (each has its parameter dropped: no gaussian pass exists, a gradient lands as its first stop flat, a layer's blend mode is never applied); `Shadow`/`Text` → `Limited`; `Clip` → `Emulated`; `Image` → `Native`. Vello: `Mask` → `Unavailable` (its coverage is applied by neither backend), `Blur`/`ColorMatrix`/`Text` → `Limited` (a *nested* filter layer draws unfiltered; an unregistered font's run is skipped). `HeadlessRenderer` claimed `Emulated` for everything while rasterizing nothing at all; it now answers `Unavailable`, like every other null object here. Both backends' render paths call `unsupported_effects` against their own table and emit `RendererError::UnsupportedEffect` — constructed, on the production path — into their `DiagnosticSink`, once per effect. (That sink is a `NullDiagnosticSink` in every in-tree path; see the delivery caveat below, which qualifies this entire entry.)

One arm of that table was itself the finding reproduced, caught by the verifier and corrected: Vello answered `BlendMode → Native`, but `SceneEffect::BlendMode` names **two** inputs and `push_layer` honours one. A layer's `blend_mode()` *field* becomes a peniko `Mix`; a `LayerEffect::Blend` in the layer's *effects list* is dropped, because that list is scanned only for `Blur` and `ColorMatrix` — a parameter on the floor, reported as supported. It is now `Limited`, with the split named. The deeper problem is the domain's, and is left open: **`LayerEffect::Blend` duplicates `SceneLayer::blend_mode` and has zero producers anywhere** — a dead variant that no backend honours, which is why one conflated table arm could cover both and read as true. CPU had it right (`Unavailable`) throughout.

**The "and fallbacks" half is now emitted for text, and only for text.** It was previously met by declaration alone — the diagnostic fired only for `Unavailable`, while a `Limited` effect's restriction was merely queryable on `supports_effect`. The two halves are found differently, which is why one scan could not cover both: `Unavailable` is a property of the **backend** (the effect never happens, whatever the frame), so the table answers it; a fallback is a property of the **frame** (a `Limited` effect draws correctly until the input its restriction names is missing), so only the backend, drawing that scene, can say it bit. `EffectFallback` / `EFFECT_FALLBACK` (`render.effect.fallback`, a distinct code from `render.effect.unsupported`, so a host can route them apart) is emitted from both render paths, deduplicated per effect **and reason** — two runs missing two different fonts are two reports; the same gap every frame is one.

`Text` was chosen because it is the only `Limited` arm on **both** backends, it is runtime-conditional, and its Vello form is the costliest thing here to discover by looking: an uncovered run is **dropped in silence**, so there is no artifact on screen to notice. Each backend's scan mirrors **its own** paint path rather than a shared guess — CPU demands an exact registry hit whose bytes `skrifa` accepts (`has_outlines_for`), Vello mirrors `font_for`, which falls back to the primary id `0` (`can_draw_text`) — because a scan that disagrees with the paint path reports a fallback that did not happen, or stays quiet about one that did, which is the defect this diagnostic exists to end. Both are pinned by tests that fail disjointly when each half is neutered.

**Still open — the `Limited` arms that remain declared, not emitted.** Naming them, because "fallbacks are explicit diagnostics" is *not* fully met: Vello's `Blur`/`ColorMatrix` (a **nested** filter layer is drawn unfiltered — the converter would have to report that it could not peel the layer, which it currently does not track); Vello's `BlendMode` (a `LayerEffect::Blend` is dropped — undiagnosed, though the variant has zero producers anywhere); and CPU's `Clip` `Emulated` allocation-failure path, which falls back to the parent mask silently. CPU's `Shadow` is the one `Limited` arm needing nothing further: `blur` is its **only** dropped parameter (`spread`/`offset`/`inset`/`radii`/`color` are all forwarded — verified against the arm, not assumed), and `Blur → Unavailable` already emits whenever the radius is positive.

**Still open — Vello's text scan is narrower than the CPU's, and deliberately so.** `can_draw_text` is a registry lookup that does not parse, because `font_for` does not parse: registering **unparseable** bytes satisfies the scan and raises nothing. Worse than un-diagnosed, that case **panics** — `vello::DrawGlyphs::draw` (vello-0.9 `scene.rs:626`) unwraps `FontRef::from_index`, so a host that registers junk bytes crashes the backend rather than degrading. That is a pre-existing robustness bug, independent of this entry (nothing here touches the draw path), found by a test that tried to register junk; it is **not fixed**. The CPU backend has no such hole — it parse-checks, and its scan mirrors that.

**Still open — and this qualifies the whole entry: no in-tree code installs a renderer sink, so today every one of these diagnostics lands in a `NullDiagnosticSink`.** The construction is real and on the production path — that much this entry's first round got right — but "reaches a host `DiagnosticSink`" overstated the delivery, and the check is the campaign's own rule: every call to `CpuRenderer::set_diagnostic_sink` / `VelloRenderer::set_diagnostic_sink` sits below its module's `#[cfg(test)]` gate (`cpu_renderer.rs:1327`, `vello_renderer.rs:1014`); no example, host, or runtime calls either. Nor can the runtime: **`UiRuntime` holds no renderer at all**, and `set_diagnostic_sink` is a backend-*inherent* method — the `Renderer` port (`id`/`capabilities`/`render`/`supports_effect`) has no sink, so a generic host cannot install one through it. An out-of-tree host that constructs a concrete backend *can*, and the emission does not branch on whether anyone is listening (the same null-object pattern §1-A uses deliberately). But "explicitly diagnosable" is, in this tree, *reachable* rather than *reached*. Closing it means putting the sink on the port, which changes the port for every implementor and was not attempted here.

**Still open — the vocabulary covers effects, not every compositing parameter:** `SceneLayer::transform()` and `LayerEffect::Opacity` are read by **neither** backend, and the Porter-Duff `composition` is honored by Vello but dropped by the CPU — none of the three is diagnosable through the table or either scan. (Nothing in the tree emits them today, which is why they do not currently mis-render.)

**5-B. §5.18 has no font subsystem, and the shaper's metrics are fake.** — **fake metrics CLOSED; installer + test fonts + Linux enumeration CLOSED; the bundled WASM fallback set is a DOCUMENTED DEVIATION (below), and macOS/Windows enumeration remain open.** The original charge: no system font enumeration (zero fontconfig/font-kit/core-text/DirectWrite); **zero font files in the repo**; and "usable rendering out of the box" false, because `SceneCoordinator::new()` installs a **mock** shaper, an empty resolver and a single-run itemizer (⇒ **no bidi by default**). The runtime's defaults are unchanged and still mock — that is deliberate (headless determinism), and `KitBootstrap::install_text_stack` is now the one call that replaces them.

The metrics half was: `HarfrustShaper::without_font()` — the only wired real mode — shaped real glyph *advances* while reporting **idealized 0.8/0.2 line metrics**, because `FontRegistry` read the real `ascent`/`descent` at registration and never plumbed them to `line_metrics_for`. Real text, fake line boxes, in every example.

Now: `FontRegistry::face_metrics()` hands the registry's real per-face `head`/`hhea` metrics to `HarfrustShaper::with_faces()` as a `FaceMetrics` snapshot keyed by `FontId`, so `line_metrics`/`line_metrics_for` scale each face's *own* ascent/descent/line-gap — a taller fallback face grows its line box (CSS 2.1 §10.8.1). All 27 examples wire it; the rendered PNGs change. The idealized ratios remain **only** for a face with no readable metrics, and each such query is counted by `HarfrustShaper::idealized_line_metrics()`.

**The installer half is now closed.** `KitBootstrap::install_text_stack(&mut runtime, &FontSet)` replaces all three inert defaults in one call — mock shaper → `HarfrustShaper`, empty resolver → a `FontRegistry` over the given faces, single-run itemizer → `UnicodeTextItemizer` — and takes the `face_metrics()` snapshot *after* registering every face, which is the step (e) below warned about. It returns `InstalledFonts`, the `(handle, bytes)` table the host feeds to its renderer's `register_font`; the runtime resolves and shapes but never rasterizes, so that hand-off cannot be closed from inside. `text-harfrust`/`text-unicode` moved into the facade's `default` feature set: the real stack was previously behind features nothing turned on, which is most of why every example hand-wired it. `tests/text_stack_install.rs` asserts the outcome, not the wiring — a line box measures Noto Sans's real 21.792px rather than the idealized 16.0px, and `direction: rtl` over `abc.` paints `.abc` (two bidi levels, Latin island preserved) where the default paints a wholesale-reversed `.cba`. Each of the four installed halves was probed by neutering it alone; they fail disjointly.

**Test fonts are vendored.** `assets/fonts/` holds Noto Sans + Noto Sans Mono (**SIL OFL 1.1**, licence and provenance beside them, `SHA256SUMS` to verify). Tests embed them with `include_bytes!` and never read the machine's fonts — on the authoring machine `fc-match sans-serif` resolves into `/usr/share/fonts/WindowsFonts/`, which is exactly the per-machine drift this removes. Note the packaged `/usr/share/licenses/noto-fonts/LICENSE` is an **unfilled Apache-2.0 template** that does not describe these binaries; the OFL is what the fonts' own `name` table (nameID 13) declares.

**Desktop enumeration exists, for Linux only.** The new `obscur-font-fontconfig` adapter shells out to `fc-match`/`fc-list` (dependency-free, the same shape as `obscur-system-linux`'s `xdg-open` provider), and `KitBootstrap::system_font_set()` reads the host's `sans-serif`/`serif`/`monospace` faces into a `FontSet`. Two behaviours are load-bearing and were verified against the tools, not assumed: `fc-match` **never fails** (an absent family returns the system default at exit 0), so named-family lookup uses `fc-list` plus a name filter; and `read_fonts::FontRef::new` **rejects `.ttc` collections** (`InvalidSfnt(0x74746366)`), so enumeration drops them rather than registering a face that would resolve nothing and make its text vanish.

**DOCUMENTED DEVIATION FROM THE SPEC — not closed, and not to be recorded as closed.** §5.18's "bundled fallback set for WASM/isolated environments" is **deliberately not met**. The kit ships no fonts in any build. Consequences, stated rather than degraded: **a WASM host that provides no font bytes and has no `queryLocalFonts()` renders no text at all.** `install_text_stack` over an empty `FontSet` installs the real adapters and paints nothing — there is no bundled set to silently substitute — and `an_empty_font_set_installs_the_real_stack_and_paints_no_text` pins that. The WASM path is that the **host supplies bytes**: `FontSet` is ordinary data built from bytes obtained anywhere, needing no filesystem. `queryLocalFonts()` is **not built**; it is Chromium-only, permission-gated, secure-context-only and async, so it is a progressive enhancement and could never be the baseline.

**Still open:** (a) **macOS and Windows enumeration are not implemented** — no Core Text, no DirectWrite; `system_font_set()` returns `None` there and no text paints from that path. Both want a real platform API rather than a CLI shell-out. (b) `queryLocalFonts()` is unbuilt (above). (c) **Font collections (`.ttc`) are unsupported** — the enumeration drops them, so a host whose only face for a script is a collection (common for CJK) gets no face for it. (d) `idealized_line_metrics()` is still an affordance, not a report — nothing in the runtime reads it, so a host that never asks still gets ratio-sized line boxes silently. (e) only `hhea` is read — the OS/2 `USE_TYPO_METRICS` selection between `sTypoAscender`/`usWinAscent` is not implemented. (g) **no RTL face is vendored** — neither Noto face covers Arabic or Hebrew, so bidi *itemization and reordering* are tested but RTL *shaping* is not. (h) an uncovered character (e.g. Han with only these faces installed) shapes to **zero glyphs and silently disappears** rather than painting `.notdef` — found while testing this, out of scope here.

**`ch` is now partly closed.** With a real fixed-pitch face vendored, `ch` measures the face's true `0` advance at layout/use time: `25ch` in Noto Sans is 228.8px (`ch_width_for` → `measure_ch_width` shapes the `0` glyph), and the mono face's 9.6px against `ch_base`'s 8.0px substitute is the 20% error the substitute's doc warns about — both now pinned by tests. **Still symbolic where round two left it:** `font-size: 2ch` still resolves to the parent's font-size at computed-value time (`absolutize.rs:234`), because the `0` glyph must be shaped in *this* node's face, which no computed-value-time context can reach. Closing that needs the measurement threaded into computed-value time — a real change to the fold's contract, not a wiring gap. One caveat worth recording so it is not "fixed" back: `MockTextShaper::ADVANCE_RATIO` is `0.6` and Noto Sans Mono's `0` is `600/1000` upem, so the mock and the real mono face agree on `1ch` **exactly, at every size** — a mono `ch` test against the mock baseline is vacuous, which is why the discriminating test uses the sans face (572/1000).

**5-C. §5.19 is a complete, tested, entirely unused subsystem.** ~1,150 lines (`PathCache`/`GlyphCache`/`TextureCache`, `CacheBudget`/`EvictionPolicy`/`CacheStatistics`/`VisibilityPriority`) with zero consumers. The caches that run are unbounded `HashMap`s with no budget, eviction, metrics or test switch. — **PARTLY CLOSED: the policy tier (`obscur_resources::cache`) now runs on one production cache — the runtime's decoded images, which is where the bytes are. The three Vello caches are untouched and still have zero consumers; the finding's premise about the text caches was wrong, and the reason is a real shape mismatch. All stated below.**

**What the tier now bounds.** `UiRuntime::image_cache` was `HashMap<Box<str>, SceneImage>` — decoded RGBA8, `w × h × 4` bytes per URL, inserted by `resolve_background_images`/`resolve_element_images` and **never removed** except by a wholesale `clear()` on a provider swap. Every distinct image an app ever showed stayed resident for the life of the process; that is the "grows without limit" the finding names, and it was the only live cache with unbounded *bytes*. It is now `runtime/image_cache.rs`, which composes the domain tier rather than reimplementing it: `CacheBudget` rules admission, `EvictionPolicy` picks the victim from `CacheEntry` bookkeeping, `CacheStatistics` carries live bytes/entries plus hit/miss/eviction counters, and `CacheKey::for_resource(handle.id())` reuses the `ResourceId` the hub already minted per URL. Those counters now reach a client: the §7.6 `Caches` inspectable reports resident bytes and the hit/miss/eviction totals, not just a count — the first pass wired the metrics to a getter (`image_cache_statistics()`) whose only caller was a test, which is the same *affordance, not a report* this audit charges against `idealized_line_metrics()` in 5-B(c), and the verifier caught it. `set_image_cache_budget` / `image_cache_budget` / `set_image_eviction_policy` / `image_cache_statistics` are the host surface. **The default is `CacheBudget::unlimited`**, so a host that asks for nothing gets byte-identical behaviour to before.

Two things make it a cache rather than a leak with a counter. Eviction **releases the hub handle**: `image_handles` is the "already requested, do not retry" guard, so an evicted URL left in it would silently never paint again — `release_evicted` is what lets a still-referenced image reload. And `mark_image_visibility` scores every resident URL against the frame's own boxes and viewport each compose, so `VisibilityPriority` is derived from real geometry, not defaulted: eviction drops what nothing is showing before what the frame is painting.

`crates/facade/obscur-kit/tests/image_cache_budget.rs` proves it from outside: real PNGs, the real `FsResourceLoader`, the real decoder, real `render_now` frames, and **no test touches the cache** — every insert and eviction is a side effect of composing. Reverting each half fails it disjointly (budget → the budget + visibility tests; visibility marking → only the visibility test; handle release → only the reload test). The visibility test is not a coin flip: document order makes the off-screen image the *more recently used* of the two, so recency alone would evict the visible one.

**Still open — this closes one cache, not §5.19.**

(a) **`PathCache`/`GlyphCache`/`TextureCache` are exactly as unused as the finding says, and were not wired.** They are unbounded `HashMap<u64, V>` newtypes implementing *none* of §5.19 — no budget, eviction, metrics or switch — and having the right names is not having the right interface. Wiring them is not a cache problem but a renderer one: the Vello backend builds a fresh `Scene` every frame and holds nothing across frames, and nothing anywhere hashes a `Path`'s geometry, so the `u64` key has no producer. Their doc headers claimed §5.19 and have been corrected to state that they meet none of it and have no callers; the decision to make the renderer stateful or to delete them is unmade.

(b) **The finding's claim that "the caches that run are unbounded `HashMap`s" is not true of the text caches, and they are the reason the tier could not simply be applied everywhere.** `CachingShaper` (`MAX_ENTRIES = 1024`) and `ParagraphShaper` (`512`) both cap entries and flush the whole map when full. That is crude — a flush is not eviction, and neither has a byte budget, metrics, or a disable switch — but it is not unbounded. They are **not** candidates for this tier, for a stated reason rather than an aesthetic one: `CacheKey` is `(ResourceId, variant)`, and a shaping request has no `ResourceId` — it is keyed by text + size + face, which no resource ever loaded. Reaching the tier from `obscur-text` would also invert the layering: `obscur-text` depends on `obscur-geometry` alone, `obscur-resources` sits *above* it in the spec's own domain order (§2.12, 10 then 11), and the rule is "domain → foundation + explicitly approved lower domain". The tier fits precisely where a `ResourceId` already exists, which is the resource caches — which is where it went. Giving the shapers real budgets needs either a second, key-generic store or a byte cap of their own; neither is this tier.

(c) `vector_cache` (parsed `SceneVector` documents) is still a bare unbounded `HashMap` on the same frame path. Vector geometry is far smaller than decoded pixels, but the cache is unbounded and its byte size is not derivable the way `SceneImage::pixels().len()` is — it would need a size estimate over path verbs. Not done.

(d) **Two more caches with zero consumers, not named in the original finding**: `obscur_style::invalidation::StyleCache` and `obscur_layout::invalidation::LayoutCache` — both complete, both tested, both reachable only through a `pub use`. `StyleCache` even implements the §5.19 disable switch that this finding says the live caches lack. The style/layout phases recompute from scratch every frame instead.

(e) §5.19's **per-cache disable switch** is only half met for the image cache. `CacheBudget::disabled()` reaches it and admits nothing, but this cache is the *residency store* compose paints from, not a memo of something compose could recompute — so disabling it means "no image is ever resident and none paints", not "run the uncached path". There is no uncached path to fall back to. Documented at the call site; a real switch would need synchronous decode-on-demand.

(f) `VisibilityPriority::NearViewport` is never produced — it needs a prefetch margin the runtime has no notion of. And §5.19's other named caches — paint/display-list, gradients, masks, the optional raster cache — do not exist at all.

**5-D. `Clip::Mask` does the opposite thing on each backend** — CPU shows the content, Vello hides it — and **no cross-backend golden test exists** to catch it. §5.2 names clipping as a must-match property. — **CLOSED: `Clip::Mask`, plus two sibling divergences (empty-path clip, and the layer clip the CPU ignored). Mask *coverage* and layer blend mode remain open, both stated below.**

The domain settles which backend was right. A `Mask` "does **not** carry the source itself" (`mask.rs:8`), and `Clip::bounds()` is `None` for a mask because "a mask's extent depends on its source content, **which is not known to the clip itself**" (`clip.rs:58-59`). A mask clip states *no extent*, so a backend may not invent one — least of all the empty extent, which discards the content. **CPU was right; Vello was wrong** (`clip_converter.rs:50`, `Clip::Mask(_) => BezPath::new()`). Vello's own `push_layer` already used an unbounded rect for a mask, so the file contradicted itself, and the converter's doc claimed "an empty shape clips away nothing" — the exact opposite of what Vello does with one. Vello's mask clip now resolves to that same unbounded outline, and both of its clip paths route through one rule instead of two.

**Sibling found and fixed (reverse polarity).** An **empty/degenerate path clip** diverged the same way and the correct answer is the *opposite*: the CPU inherited the parent clip and painted (`cpu_renderer.rs`, `to_sk_path` → `None` → `parent.cloned()`) while Vello admitted nothing. Here the extent *is* stated, and stated to be empty, so nothing may pass — Vello was right and the CPU now pushes an all-zero mask. "No bounds known" (mask) and "bounds known to be empty" (empty path) are opposite instructions that both reach a backend as an absence, which is how one line served both. A zero-area *line* path and a zero-size *rect* already agreed (both admit nothing); only the `to_sk_path` → `None` cases diverged.

**The missing test now exists**, and it is the half that matters: `crates/facade/obscur-kit/tests/clip_cross_backend.rs` drives the same scene through both backends across every `Clip` variant and asserts they agree *and* that the shared answer is the one the domain requires. Both backends are wired as **unconditional dev-dependencies** of `obscur-kit` — `render-vello` is not a default feature, so a feature-gated test would be skipped by a plain `cargo test --workspace`, which is the silence that let this bug live. Reverting each half fails it disjointly.

**What the test does not cover:** it compares Vello's *clip geometry* against the CPU's *rasterized coverage*, not Vello pixels against CPU pixels. Vello's rasterizer needs a GPU and this workspace has **no GPU test target at all** (every GPU proof in `obscur-kit` is a hand-run `[[example]]`), so a readback `#[test]` would silently no-op on GPU-less CI. §5.2 puts rasterization/AA in *allowed differences* and clipping/scene-geometry in *must match*, so the GPU-free clip decision is the property §5.2 actually constrains — but this is a real gap, not a complete golden test. Clip **nesting** and paint order are not compared either.

**The third divergence — larger than the one above — is now CLOSED.** `SceneLayer::clip()` was **honored by Vello and ignored by the CPU backend**, whose `PushLayer` applied only `opacity` ("the layer's own clip / blend-mode / transform / effect fields are not honored here"). The CPU backend now resolves a layer clip through `resolve_clip_entry` — the *same* rule `PushClip` uses, extracted rather than duplicated, so the two deliveries of a clip cannot drift — and pops it at `PopLayer`. Both CPU layer paths are covered: a reduced-opacity layer (offscreen buffer) and a trivial one (passthrough). The offscreen is allocated at the parent's dimensions, so a surface-space mask is valid inside it.

Two tests pin it, and they fail **disjointly** when each half is neutered: `backends_agree_when_the_clip_rides_on_the_layer` (reproducing the audit's own empirical symptom — a layer clipped to `(16,16)-(48,48)` painting at `(4,4)`) and `a_layer_clip_does_not_outlive_its_layer`. The second exists because the first could not see a missing pop: a single-bracket scene never draws after `PopLayer`, so the push half alone passed it — the "one half carrying the other" failure this campaign warns about, caught by probing the halves separately.

**Still open — mask coverage:** **neither backend implements it at all** — both *ignore* it identically, which is the §5.8 fallback, so a masked region paints unmasked on both. It is **no longer silent**, and 5-A is why: `Clip::Mask` lowers to `SceneEffect::Mask` (`effect_report.rs:305`), both tables answer `Unavailable` (`cpu_renderer.rs:614`, `vello_renderer.rs:997`), and both render paths emit `unsupported effect: mask` (`cpu_renderer.rs:326-328`, `vello_renderer.rs:244-246`), pinned by `rendering_an_unsupported_effect_tells_the_host_which_one` (`vello_renderer.rs:1056`). Two caveats keep this open rather than closed: the report is `Unavailable`, **not** the §5.8 *fallback* diagnostic an explicit fallback is supposed to carry; and 5-A's delivery caveat applies, so in-tree it lands in a `NullDiagnosticSink`. `clip_converter.rs:40-43`'s doc still claims neither backend raises it — stale, and wrong in the code.

**Still open — layer blend mode / composition, found by the sibling sweep and deliberately not fixed:** Vello maps `layer.blend_mode()` / `layer.composition()` onto a `peniko::BlendMode`; the CPU backend reads **neither** and composites its offscreen with `PixmapPaint { opacity, ..Default::default() }`, i.e. always source-over. A `Multiply` layer would therefore multiply on Vello and not on CPU. This is a **lower-priority** divergence than the clip for two checked reasons, not by assumption: §5.2's must-match list names *clipping*, paint order, and scene geometry — **not** blend mode; and `with_blend_mode`/`with_composition` have **zero production producers** — outside their defining file (`scene_layer.rs`, whose four call sites all sit below its gate at 146) their only two call sites (`effect_report.rs:436`, `scene_converter.rs:1072`) both sit below their module's `#[cfg(test)]` gate (lines 334 and 1012). So it is real in the backends but currently unreachable from production, unlike the layer clip, which had a live producer. Left open rather than fixed silently. **Layer transform** is ignored by *both* backends, so it does not diverge (both are incomplete, consistently).

**7-B. ~~The headless runtime's determinism is ceremonial.~~** — closed. The root cause was structural, not a missing call: `HeadlessHost` wrapped `FramePipeline`, which is a *pure function* of `(tree, view, inputs, viewport)` with no clock and no async seam, so the host's clock and executor could not have reached a frame however they were called. The seams exist one layer up, on `UiRuntime` (`advance_motion`, `set_blocking_executor`), so `HeadlessHost` now **drives a real `UiRuntime`**:

- `advance_time` advances the clock and hands the delta *derived from the clock's own readings* to the runtime's motion scheduler, so an animation's sampled value reaches the next frame's layout and paint. `advance_time_drives_an_animation_into_the_next_frames_layout` fails (width pinned at 0) when that one line is cut; `without_advance_time_a_frame_never_moves` guards the converse.
- The host installs its `DeterministicExecutor` as the runtime's blocking port, so a frame's resource load is *queued* instead of run inline, and `run_tasks` runs it **and** drains the completion. Three tests cover it, and they fail disjointly: cutting the install fails all three, cutting only the drain fails just the two that assert the load lands.
- `DeterministicExecutor` was `RefCell`-based and therefore **not `Send + Sync`** — it could not satisfy `set_blocking_executor`'s bound at all, which is why `ui_runtime.rs`'s own tests hand-rolled a `Mutex`-based `QueuedExecutor` clone of it. The two vacuous tests are gone: `run_tasks_drains_the_executor` (which spawned its own closure) is replaced by the resource-load tests, and `advance_time_moves_the_clock` is kept but demoted to what it always was — a clock unit test that, verifiably, still passes with the motion wiring cut.

**Still open under 7-C:**
