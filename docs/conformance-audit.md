# obscur.kit_v2 — Spec Conformance Audit

- **Date:** 2026-07-15
- **Commit:** `f01df9d` (+ the fixes this audit prompted; see *Fixed during the audit*)
- **Workspace:** `cargo run -p xtask -- check` clean; 63 packages; 4,629 tests passing; 412 commits.
- **Method:** 9 parallel read-only audits — one per spec chapter §1–§9, plus a cross-cutting orphan sweep. Each derived its requirements from the chapter text (quoting the line), then verified against the code at HEAD with `file:line` evidence.
- **Supersedes** the 2026-07-15 audit at `f074dba` (47 commits earlier). That audit is superseded rather than amended because its central claims were **systematically too generous**, in one specific and repeatable way — see below.
- **Tiering:** **Tier-1** = actively wrong (produces incorrect output while reporting success) or core-required missing. **Tier-2** = spec-required, real gap. **Tier-3** = deferred / documented policy / honest placeholder.

## Why this audit exists

The previous audit called §5 "genuinely wired end-to-end" with "none" Tier-1, and recorded the "built but not wired" theme as "largely closed". Both are false, and the *reason* they are false is the finding that matters most:

> **A type existing is not evidence that anything calls it — and a doc comment asserting the wiring is how a reviewer gets convinced otherwise.**

Three doc comments in this codebase assert an architecture that is not connected:

- `child_measurer.rs:19` — leaves "route to the intrinsic-measure port `IntrinsicMeasure`". They do not; `IntrinsicMeasure` has no production consumer.
- `layout_invalidation.rs:12` — "the structured replacement for scattered ad-hoc dirty flags". The shipped model *is* four booleans.
- `frame_budget.rs:15` — "the emitted `Diagnostic` flows through the normal diagnostics channel". Nothing emits, and there is no channel.

This audit therefore treats **"who calls it?"** as the primary question, and reports a doc that describes an unbuilt mechanism as a finding in its own right.

### The dominant pattern

**The domain crates are richer than the runtime that consumes them.** Roughly a third of `obscur-layout`, all of `obscur-system`, all of `obscur-routing`, all of `obscur-windowing`, the whole diagnostics subscription tier, the whole record/replay tier, and — until 5-C put the §5.19 policy tier on the runtime's decoded-image cache — every §5.19 cache compile, pass tests, and are called by nothing. The three Vello caches, `StyleCache` and `LayoutCache` still are.

The structural cause is visible in one file: **`crates/facade/obscur-kit/src/lib.rs` is a re-export barrel** (lines 30–105 are `pub use X as y;` and nothing else). Anything whose only path to the outside is that file is unwired by construction. That is what hid `obscur-data-transfer` from the last audit; it now accounts for `obscur-system` and `obscur-routing` wholesale.

## Tier-1 findings

### §1 — the dynamic architecture has no execution path

**1-A. A component render failure keeps stale UI and is reported on no channel.** — **fixed for component renders.**
Was: `let Ok(view) = mounted.render(..) else { errors += 1; continue; }`, and that `continue` was the whole of §1.7. Now `MountedComponent` owns an `ErrorBoundary` built from the author's `error_boundary()` and a new `Component::fallback()`, and `render` returns `GuardedRender` — the boundary's decision, taken via `ComponentRecovery`, never a raw `Result`. `render_components` enacts it: a retry leaves the subtree and schedules the frame that spends the budget, an exhausted budget commits the fallback *over* the subtree, and a disabled boundary propagates to the nearest enclosing enabled one, whose subtree is replaced instead. `ErrorBoundaryPolicy::disabled()` now differs from enabled on every axis.

Still open, and deliberately: two paths still leave the last output standing. A **retry** does for the frames the budget buys (that is what a retry *is*), and a **propagated failure with no enclosing enabled boundary** does indefinitely — every boundary that could have answered was disabled. Both are reported; neither is silent. `SubsystemRecovery` remains uncalled, so §1.7's "layout, renderer and resource failures use subsystem-specific recovery boundaries" is still unbuilt.

**1-B. No production code in this workspace ever constructs a `Diagnostic`.** — **fixed for this path only.**
`MountedComponent::contain` builds one (via `ComponentFailure`) under a stable `view.component.props` code, and `UiRuntime::report_failure` stamps the two §1.6 fields only the runtime knows — the node it concerns and the `RecoveryAction` actually taken — before emitting to a `DiagnosticSink` installed by `set_diagnostic_sink`. A test drives it through the shipped `ChannelSink`/`DiagnosticChannel` to a filtered subscriber, so the §7.8 subscription path is exercised end-to-end rather than asserted. The default is a `NullDiagnosticSink`, so the failure path does not branch on whether anyone listens.

This is the *only* producer. Every other subsystem still reports through its own path (a `BudgetViolation`, a `Result`, a last-good value); routing those through the sink is separate work.

**1-C. The kit cannot create a window (§1.4 R8).**
`obscur-runtime` does not depend on `obscur-windowing`. `WinitWindowBackend` (526 lines) has zero consumers; the one example that opens a window says in prose that it does not use it (`windowed_counter.rs:22-25`). Overlay mode (R10) has no representation.

### §2 — the primary authoring surface is unchecked

**2-A. §2.13 is unenforced where it matters.** Three compounding gaps: the `okui!` macro — self-declared "the spec's *primary* authoring surface" — runs **no** contract validation; the `.okui` path skips any tag with no registered contract; and `register_surface` is called only from a test, so no user component's contract can be checked. "Unknown attributes… are compile errors" holds only for the 20 hard-coded built-in tags, and only on the file path.

**2-B. Dynamic text bindings are silently wrong on both front ends.** ~~`okui! { <div>{user.name}</div> }` renders the literal text **`"user.name"`** (`dsl_macro.rs:138`), and a test at `:551` *asserts the bug*. The `.okui` path renders an empty box.~~ **Closed on the codegen path, which is both front ends' production path.** They now build one `UiIrNode::interpolation` carrying the expression, and `ViewCodegen` emits `ViewNode::text(ToString::to_string(&(user.name)))` — the same "a binding is a Rust path" design `d1a11bc` gave attributes. The test that asserted the bug is inverted; `okui_text_binding.rs` proves the value renders, through the real macro with real locals. Two things stay open, neither introduced by that fix:

- `document_to_view_fn` emits a *nullary* `pub fn <name>() -> View`, so a compiled file's bindings can only name what the generated module has around it. A file whose bindings read per-call state does not compile — the function has no parameters to read it from — and giving it them needs a props-signature decision nothing makes yet. This has bounded every `.okui` file binding since `d1a11bc`; text is not special.
- `UiIrViewBridge`, the *interpreter*, still renders an interpolation as an unknown element (an empty box) and still lowers an attribute binding to its path's spelling. It cannot do better by construction — there is no Rust scope to resolve a path in at runtime — and it has no production consumer (tests plus `showcase_okui_png`). A binding is a compile-time construct here; the bridge is the artifact of that.

**2-C. §2.12 is unimplemented below the type layer.** `ViewNode` does not model slots (one anonymous `children`); `SyntaxKind` has no slot node; `SlotContract`/`SlotCardinality`/`StylePartContract` have zero production consumers; `Template::slot_names()` and `SymbolKind::Slot` are dead. Nothing parses, validates or routes a slot.

**2-D. `<VirtualFor>` is `<For>` with a different spelling.** Parsed, classified, lowered with its tag — and `emit_loop` never reads the tag. A tag whose entire purpose is a performance contract, honoured by nothing, with no diagnostic.

### §3 — invalidation is boolean-per-phase

**3-A. §3.4 step 8 "incremental layout" does not exist.** Every node payload in the chain — `UiOperation::{Rerender,InvalidateStyle,InvalidateLayout}.node`, `Invalidation::node()`, `StyleInvalidation::invalidate(node,…)`, `LayoutInvalidation::invalidate(node,…)` — is **write-only**. No production reader of `is_invalidated`/`reason` exists. Both phase consumers (`StyleCoordinator::resolve`, `LayoutCoordinator::layout_editing`) take no dirty set and walk the whole tree. A hover on one node ⇒ full restyle of every node. §4.3 closes with *"Scattered ad hoc dirty flags are not the architectural model"*; the shipped model is `style_dirty`/`layout_dirty`/`scene_dirty`/`paint_dirty`.

**3-B. §3.1 dependency tracking is wired to nothing and defeated downstream.** `ComponentContext::track` must be called by hand and its only call site is a test. `notify_signal`/`register_component` are called only from tests; every example uses `set_root_view` (whole-view rebuild). Even if used, `run_due_frame_reactive` hardcodes `FrameReason::UiCommit` → `FramePlan::full()`, erasing `render_components`' genuine incrementality one phase later.

**3-C. §3.7 is 100% stubs.** Six placeholder structs. No runtime lifecycle, no shutdown, no release path.

### §4 — relative units die at the layout↔paint seam

**4-A. `font-size: 2rem` renders at 16px, and poisons every `em` on the node.**
`ComputedStyle` never absolutizes lengths. Layout resolves via `resolve_px(ctx)`; **paint does not** (`scene_coordinator.rs:2812,3317,3635` use `as_px()`, which honours absolute px only). Consequences: `border-width: .1em` **reserves layout space and paints nothing** — the two phases disagree; `box-shadow`/`border-radius`/`blur` in relative units become 0; `border-radius: 50%` (the circle idiom) is dead. `rem` has no chicken-and-egg excuse. **One absolutization pass at computed-value time retires ~8 silently-wrong rows.**

**4-B. `@container` always matches.** — **CLOSED (fails closed + diagnostic); still not implemented.** Was: full parse→lower→evaluate chain exists, but `MediaEnvironment::with_container` has **zero callers** and there is no `container-type` property, so unset ⇒ non-restrictive ⇒ holds — failing open, the worst mode for a gate.

Now: an unknown *container* axis evaluates to **false** (`FeatureQuery::holds`), an unrepresentable container feature lowers to `Never` rather than `Always`, a bare `@container name { … }` lowers to `Never`, and the parser records an `UnsupportedCssFeature(AtRule, "@container")` on `CompiledStylesheet::unsupported`. Viewport axes keep their permissive `unbounded()` opt-out — the asymmetry is deliberate and documented (css-contain-3 §3.1).

Two scoping caveats, or this entry becomes the next over-claim: "inert" covers **matchable declarations**; the motion path (`stylesheet_compiler.rs:404-409`) is a separate lowering. And the diagnostic is **recorded, not reported** — `unsupported` has no production reader (every consumer takes `.matchable`), which is the same decorative-diagnostics finding §5-A records.

**Still open:** `@container` rules are *inert*, not *working*. There is no `container-type`/`container-name` property, and `with_container` still has no production caller. Wiring it for real needs a container's resolved size during matching, but `build_inputs_env` matches the whole tree strictly *before* `style.resolve` and layout, and there is no layout-interleaved restyle pass. §4.13 listing container queries as *Supported* remains an over-claim against the implementation.

**4-C. `::before`/`::after` apply their declarations to the originating element.** `selector_matcher.rs:134`: `PseudoElement(_) => true`. `.badge::before { color: red }` paints `.badge` red. No `PropertyId::Content`, no generated box. Omission would fail closed; this does not.

**4-D. Intrinsic sizing is flow-`width`-only.** `is_intrinsic` has exactly one production caller. So `min-/max-width: min-content` applies **no clamp at all**; flex `flex-basis`/`width: <intrinsic>` degrades to `auto`; `grid-template-columns: min-content` **drops the entire track list**.

### §5 — no font subsystem; caches dead; diagnostics decorative

**5-A. §5.2's "explicit diagnostics" requirement is decorative.** — **CLOSED for `Unavailable` effects, and for the one `Limited` fallback both backends share (text); the remaining `Limited` arms are declared, not emitted, and are named below.** `RendererError::UnsupportedEffect` was **never constructed**; `Renderer::supports_effect` had no production consumer. The previous audit converted this into a clean bill of health ("documented policy, correctly reported via `supports_effect`") — nothing read it, and what it reported was wrong: CPU claimed `Emulated` for blur while `DrawShadow` destructures `blur: _` and draws a hard rect. **That is `Unavailable`.**

Now: the effect vocabulary is closed (`SceneEffect`), so each backend's table is an exhaustive match the compiler checks and every arm was re-derived from the paint path. CPU: `Blur`/`BackdropFilter`/`ColorMatrix`/`Gradient`/`Mask`/`BlendMode` → `Unavailable` (each has its parameter dropped: no gaussian pass exists, a gradient lands as its first stop flat, a layer's blend mode is never applied); `Shadow`/`Text` → `Limited`; `Clip` → `Emulated`; `Image` → `Native`. Vello: `Mask` → `Unavailable` (its coverage is applied by neither backend), `Blur`/`ColorMatrix`/`Text` → `Limited` (a *nested* filter layer draws unfiltered; an unregistered font's run is skipped). `HeadlessRenderer` claimed `Emulated` for everything while rasterizing nothing at all; it now answers `Unavailable`, like every other null object here. Both backends' render paths call `unsupported_effects` against their own table and emit `RendererError::UnsupportedEffect` — constructed, on the production path — into their `DiagnosticSink`, once per effect. (That sink is a `NullDiagnosticSink` in every in-tree path; see the delivery caveat below, which qualifies this entire entry.)

One arm of that table was itself the finding reproduced, caught by the verifier and corrected: Vello answered `BlendMode → Native`, but `SceneEffect::BlendMode` names **two** inputs and `push_layer` honours one. A layer's `blend_mode()` *field* becomes a peniko `Mix`; a `LayerEffect::Blend` in the layer's *effects list* is dropped, because that list is scanned only for `Blur` and `ColorMatrix` — a parameter on the floor, reported as supported. It is now `Limited`, with the split named. The deeper problem is the domain's, and is left open: **`LayerEffect::Blend` duplicates `SceneLayer::blend_mode` and has zero producers anywhere** — a dead variant that no backend honours, which is why one conflated table arm could cover both and read as true. CPU had it right (`Unavailable`) throughout.

**The "and fallbacks" half is now emitted for text, and only for text.** It was previously met by declaration alone — the diagnostic fired only for `Unavailable`, while a `Limited` effect's restriction was merely queryable on `supports_effect`. The two halves are found differently, which is why one scan could not cover both: `Unavailable` is a property of the **backend** (the effect never happens, whatever the frame), so the table answers it; a fallback is a property of the **frame** (a `Limited` effect draws correctly until the input its restriction names is missing), so only the backend, drawing that scene, can say it bit. `EffectFallback` / `EFFECT_FALLBACK` (`render.effect.fallback`, a distinct code from `render.effect.unsupported`, so a host can route them apart) is emitted from both render paths, deduplicated per effect **and reason** — two runs missing two different fonts are two reports; the same gap every frame is one.

`Text` was chosen because it is the only `Limited` arm on **both** backends, it is runtime-conditional, and its Vello form is the costliest thing here to discover by looking: an uncovered run is **dropped in silence**, so there is no artifact on screen to notice. Each backend's scan mirrors **its own** paint path rather than a shared guess — CPU demands an exact registry hit whose bytes `skrifa` accepts (`has_outlines_for`), Vello mirrors `font_for`, which falls back to the primary id `0` (`can_draw_text`) — because a scan that disagrees with the paint path reports a fallback that did not happen, or stays quiet about one that did, which is the defect this diagnostic exists to end. Both are pinned by tests that fail disjointly when each half is neutered.

**Still open — the `Limited` arms that remain declared, not emitted.** Naming them, because "fallbacks are explicit diagnostics" is *not* fully met: Vello's `Blur`/`ColorMatrix` (a **nested** filter layer is drawn unfiltered — the converter would have to report that it could not peel the layer, which it currently does not track); Vello's `BlendMode` (a `LayerEffect::Blend` is dropped — undiagnosed, though the variant has zero producers anywhere); and CPU's `Clip` `Emulated` allocation-failure path, which falls back to the parent mask silently. CPU's `Shadow` is the one `Limited` arm needing nothing further: `blur` is its **only** dropped parameter (`spread`/`offset`/`inset`/`radii`/`color` are all forwarded — verified against the arm, not assumed), and `Blur → Unavailable` already emits whenever the radius is positive.

**Still open — Vello's text scan is narrower than the CPU's, and deliberately so.** `can_draw_text` is a registry lookup that does not parse, because `font_for` does not parse: registering **unparseable** bytes satisfies the scan and raises nothing. Worse than un-diagnosed, that case **panics** — `vello::DrawGlyphs::draw` (vello-0.9 `scene.rs:626`) unwraps `FontRef::from_index`, so a host that registers junk bytes crashes the backend rather than degrading. That is a pre-existing robustness bug, independent of this entry (nothing here touches the draw path), found by a test that tried to register junk; it is **not fixed**. The CPU backend has no such hole — it parse-checks, and its scan mirrors that.

**Still open — and this qualifies the whole entry: no in-tree code installs a renderer sink, so today every one of these diagnostics lands in a `NullDiagnosticSink`.** The construction is real and on the production path — that much this entry's first round got right — but "reaches a host `DiagnosticSink`" overstated the delivery, and the check is the campaign's own rule: every call to `CpuRenderer::set_diagnostic_sink` / `VelloRenderer::set_diagnostic_sink` sits below its module's `#[cfg(test)]` gate (`cpu_renderer.rs:1319`, `vello_renderer.rs:1004`); no example, host, or runtime calls either. Nor can the runtime: **`UiRuntime` holds no renderer at all**, and `set_diagnostic_sink` is a backend-*inherent* method — the `Renderer` port (`id`/`capabilities`/`render`/`supports_effect`) has no sink, so a generic host cannot install one through it. An out-of-tree host that constructs a concrete backend *can*, and the emission does not branch on whether anyone is listening (the same null-object pattern §1-A uses deliberately). But "explicitly diagnosable" is, in this tree, *reachable* rather than *reached*. Closing it means putting the sink on the port, which changes the port for every implementor and was not attempted here.

**Still open — the vocabulary covers effects, not every compositing parameter:** `SceneLayer::transform()` and `LayerEffect::Opacity` are read by **neither** backend, and the Porter-Duff `composition` is honored by Vello but dropped by the CPU — none of the three is diagnosable through the table or either scan. (Nothing in the tree emits them today, which is why they do not currently mis-render.)

**5-B. §5.18 has no font subsystem, and the shaper's metrics are fake.** — **fake metrics CLOSED; the font subsystem is untouched.** No system font enumeration (zero fontconfig/font-kit/core-text/DirectWrite); **zero font files in the repo**, so the "bundled fallback set for WASM/isolated environments" cannot be met by construction. "Usable rendering out of the box" is false: `SceneCoordinator::new()` installs a **mock** shaper, an empty resolver and a single-run itemizer (⇒ **no bidi by default**). All of that stands.

The metrics half was: `HarfrustShaper::without_font()` — the only wired real mode — shaped real glyph *advances* while reporting **idealized 0.8/0.2 line metrics**, because `FontRegistry` read the real `ascent`/`descent` at registration and never plumbed them to `line_metrics_for`. Real text, fake line boxes, in every example.

Now: `FontRegistry::face_metrics()` hands the registry's real per-face `head`/`hhea` metrics to `HarfrustShaper::with_faces()` as a `FaceMetrics` snapshot keyed by `FontId`, so `line_metrics`/`line_metrics_for` scale each face's *own* ascent/descent/line-gap — a taller fallback face grows its line box (CSS 2.1 §10.8.1). All 27 examples wire it; the rendered PNGs change. The idealized ratios remain **only** for a face with no readable metrics, and each such query is counted by `HarfrustShaper::idealized_line_metrics()`.

**Still open:** (a) the font-subsystem half above — enumeration, bundled fallbacks, the mock-by-default stack; (b) `KitBootstrap` still has **no installer** — `text_shaper_without_font` now *takes* `FaceMetrics`, so metrics-blindness is opt-in rather than the default, but `FaceMetrics::empty()` is a documented opt-out that hands out exactly such a shaper (`kit_bootstrap.rs:223-226`); the constructor has zero callers regardless, and all 27 examples still hand-wire the stack identically; (c) `idealized_line_metrics()` is an affordance, not a report — nothing in the runtime reads it, so a host that never asks still gets ratio-sized line boxes silently; (d) only `hhea` is read — the OS/2 `USE_TYPO_METRICS` selection between `sTypoAscender`/`usWinAscent` is not implemented; (e) **a new silent-wrongness, narrower than the one closed**: `face_metrics()` is a *snapshot*, so a face registered after it is absent from the table, `line_metrics_for` misses, and the fall-through hands back the **primary face's** real metrics — that face is measured by the wrong font, and `idealized_line_metrics()` does not count it, because the counter only catches the idealized fallback and never wrong-face substitution. All 27 examples order their calls correctly, so nothing is wrong today; the trap is set for the 28th.

**5-C. §5.19 is a complete, tested, entirely unused subsystem.** ~1,150 lines (`PathCache`/`GlyphCache`/`TextureCache`, `CacheBudget`/`EvictionPolicy`/`CacheStatistics`/`VisibilityPriority`) with zero consumers. The caches that run are unbounded `HashMap`s with no budget, eviction, metrics or test switch. — **PARTLY CLOSED: the policy tier (`obscur_resources::cache`) now runs on one production cache — the runtime's decoded images, which is where the bytes are. The three Vello caches are untouched and still have zero consumers; the finding's premise about the text caches was wrong, and the reason is a real shape mismatch. All stated below.**

**What the tier now bounds.** `UiRuntime::image_cache` was `HashMap<Box<str>, SceneImage>` — decoded RGBA8, `w × h × 4` bytes per URL, inserted by `resolve_background_images`/`resolve_element_images` and **never removed** except by a wholesale `clear()` on a provider swap. Every distinct image an app ever showed stayed resident for the life of the process; that is the "grows without limit" the finding names, and it was the only live cache with unbounded *bytes*. It is now `runtime/image_cache.rs`, which composes the domain tier rather than reimplementing it: `CacheBudget` rules admission, `EvictionPolicy` picks the victim from `CacheEntry` bookkeeping, `CacheStatistics` carries live bytes/entries plus hit/miss/eviction counters, and `CacheKey::for_resource(handle.id())` reuses the `ResourceId` the hub already minted per URL. Those counters now reach a client: the §7.6 `Caches` inspectable reports resident bytes and the hit/miss/eviction totals, not just a count — the first pass wired the metrics to a getter (`image_cache_statistics()`) whose only caller was a test, which is the same *affordance, not a report* this audit charges against `idealized_line_metrics()` in 5-B(c), and the verifier caught it. `set_image_cache_budget` / `image_cache_budget` / `set_image_eviction_policy` / `image_cache_statistics` are the host surface. **The default is `CacheBudget::unlimited`**, so a host that asks for nothing gets byte-identical behaviour to before.

Two things make it a cache rather than a leak with a counter. Eviction **releases the hub handle**: `image_handles` is the "already requested, do not retry" guard, so an evicted URL left in it would silently never paint again — `release_evicted` is what lets a still-referenced image reload. And `mark_image_visibility` scores every resident URL against the frame's own boxes and viewport each compose, so `VisibilityPriority` is derived from real geometry, not defaulted: eviction drops what nothing is showing before what the frame is painting.

`crates/facade/obscur-kit/tests/image_cache_budget.rs` proves it from outside: real PNGs, the real `FsResourceLoader`, the real decoder, real `render_now` frames, and **no test touches the cache** — every insert and eviction is a side effect of composing. Reverting each half fails it disjointly (budget → the budget + visibility tests; visibility marking → only the visibility test; handle release → only the reload test). The visibility test is not a coin flip: document order makes the off-screen image the *more recently used* of the two, so recency alone would evict the visible one.

**Still open — this closes one cache, not §5.19.**

(a) **`PathCache`/`GlyphCache`/`TextureCache` are exactly as unused as the finding says, and were not wired.** They are unbounded `HashMap<u64, V>` newtypes implementing *none* of §5.19 — no budget, eviction, metrics or switch — and having the right names is not having the right interface. Wiring them is not a cache problem but a renderer one: the Vello backend builds a fresh `Scene` every frame and holds nothing across frames, and nothing anywhere hashes a `Path`'s geometry, so the `u64` key has no producer. Their doc headers claimed §5.19 and have been corrected to state that they meet none of it and have no callers; the decision to make the renderer stateful or to delete them is unmade.

(b) **The finding's claim that "the caches that run are unbounded `HashMap`s" is not true of the text caches, and they are the reason the tier could not simply be applied everywhere.** `CachingShaper` (`MAX_ENTRIES = 1024`) and `ParagraphShaper` (`512`) both cap entries and flush the whole map when full. That is crude — a flush is not eviction, and neither has a byte budget, metrics, or a disable switch — but it is not unbounded. They are **not** candidates for this tier, for a stated reason rather than an aesthetic one: `CacheKey` is `(ResourceId, variant)`, and a shaping request has no `ResourceId` — it is keyed by text + size + face, which no resource ever loaded. Reaching the tier from `obscur-text` would also invert the layering: `obscur-text` depends on `obscur-geometry` alone, `obscur-resources` sits *above* it in the spec's own domain order (§2.12, 10 then 11), and the rule is "domain → foundation + explicitly approved lower domain". The tier fits precisely where a `ResourceId` already exists, which is the resource caches — which is where it went. Giving the shapers real budgets needs either a second, key-generic store or a byte cap of their own; neither is this tier.

(c) `vector_cache` (parsed `SceneVector` documents) is still a bare unbounded `HashMap` on the same frame path. Vector geometry is far smaller than decoded pixels, but the cache is unbounded and its byte size is not derivable the way `SceneImage::pixels().len()` is — it would need a size estimate over path verbs. Not done.

(d) **Two more caches with zero consumers, not named in the original finding**: `obscur_style::invalidation::StyleCache` and `obscur_layout::invalidation::LayoutCache` — both complete, both tested, both reachable only through a `pub use`. `StyleCache` even implements the §5.19 disable switch that this finding says the live caches lack. The style/layout phases recompute from scratch every frame instead.

(e) §5.19's **per-cache disable switch** is only half met for the image cache. `CacheBudget::disabled()` reaches it and admits nothing, but this cache is the *residency store* compose paints from, not a memo of something compose could recompute — so disabling it means "no image is ever resident and none paints", not "run the uncached path". There is no uncached path to fall back to. Documented at the call site; a real switch would need synchronous decode-on-demand.

(f) `VisibilityPriority::NearViewport` is never produced — it needs a prefetch margin the runtime has no notion of. And §5.19's other named caches — paint/display-list, gradients, masks, the optional raster cache — do not exist at all.

**5-D. `Clip::Mask` does the opposite thing on each backend** — CPU shows the content, Vello hides it — and **no cross-backend golden test exists** to catch it. §5.2 names clipping as a must-match property. — **CLOSED: `Clip::Mask`, plus two sibling divergences (empty-path clip, and the layer clip the CPU ignored). Mask *coverage* and layer blend mode remain open, both stated below.**

The domain settles which backend was right. A `Mask` "does **not** carry the source itself" (`mask.rs:8`), and `Clip::bounds()` is `None` for a mask because "a mask's extent depends on its source content, **which is not known to the clip itself**" (`clip.rs:58-59`). A mask clip states *no extent*, so a backend may not invent one — least of all the empty extent, which discards the content. **CPU was right; Vello was wrong** (`clip_converter.rs:50`, `Clip::Mask(_) => BezPath::new()`). Vello's own `push_layer` already used an unbounded rect for a mask, so the file contradicted itself, and the converter's doc claimed "an empty shape clips away nothing" — the exact opposite of what Vello does with one. Vello's mask clip now resolves to that same unbounded outline, and both of its clip paths route through one rule instead of two.

**Sibling found and fixed (reverse polarity).** An **empty/degenerate path clip** diverged the same way and the correct answer is the *opposite*: the CPU inherited the parent clip and painted (`cpu_renderer.rs`, `to_sk_path` → `None` → `parent.cloned()`) while Vello admitted nothing. Here the extent *is* stated, and stated to be empty, so nothing may pass — Vello was right and the CPU now pushes an all-zero mask. "No bounds known" (mask) and "bounds known to be empty" (empty path) are opposite instructions that both reach a backend as an absence, which is how one line served both. A zero-area *line* path and a zero-size *rect* already agreed (both admit nothing); only the `to_sk_path` → `None` cases diverged.

**The missing test now exists**, and it is the half that matters: `crates/facade/obscur-kit/tests/clip_cross_backend.rs` drives the same scene through both backends across every `Clip` variant and asserts they agree *and* that the shared answer is the one the domain requires. Both backends are wired as **unconditional dev-dependencies** of `obscur-kit` — `render-vello` is not a default feature, so a feature-gated test would be skipped by a plain `cargo test --workspace`, which is the silence that let this bug live. Reverting each half fails it disjointly.

**What the test does not cover:** it compares Vello's *clip geometry* against the CPU's *rasterized coverage*, not Vello pixels against CPU pixels. Vello's rasterizer needs a GPU and this workspace has **no GPU test target at all** (every GPU proof in `obscur-kit` is a hand-run `[[example]]`), so a readback `#[test]` would silently no-op on GPU-less CI. §5.2 puts rasterization/AA in *allowed differences* and clipping/scene-geometry in *must match*, so the GPU-free clip decision is the property §5.2 actually constrains — but this is a real gap, not a complete golden test. Clip **nesting** and paint order are not compared either.

**The third divergence — larger than the one above — is now CLOSED.** `SceneLayer::clip()` was **honored by Vello and ignored by the CPU backend**, whose `PushLayer` applied only `opacity` ("the layer's own clip / blend-mode / transform / effect fields are not honored here"). It was never an edge case: `scene_coordinator.rs:2056` sets `with_clip(Clip::rect(bounds))` on every `filter: blur()` / color-matrix bracket, and it sits above that file's only `#[cfg(test)]` gate (line 3861), so it is genuine production code. The CPU backend now resolves a layer clip through `resolve_clip_entry` — the *same* rule `PushClip` uses, extracted rather than duplicated, so the two deliveries of a clip cannot drift — and pops it at `PopLayer`. Both CPU layer paths are covered: a reduced-opacity layer (offscreen buffer) and a trivial one (passthrough). The offscreen is allocated at the parent's dimensions, so a surface-space mask is valid inside it.

Two tests pin it, and they fail **disjointly** when each half is neutered: `backends_agree_when_the_clip_rides_on_the_layer` (reproducing the audit's own empirical symptom — a layer clipped to `(16,16)-(48,48)` painting at `(4,4)`) and `a_layer_clip_does_not_outlive_its_layer`. The second exists because the first could not see a missing pop: a single-bracket scene never draws after `PopLayer`, so the push half alone passed it — the "one half carrying the other" failure this campaign warns about, caught by probing the halves separately.

**Still open — mask coverage:** **neither backend implements it at all** — both *ignore* it identically, which is the §5.8 fallback, and **neither raises the diagnostic** §5.8 requires an explicit fallback to carry, so a masked region silently paints unmasked on both.

**Still open — layer blend mode / composition, found by the sibling sweep and deliberately not fixed:** Vello maps `layer.blend_mode()` / `layer.composition()` onto a `peniko::BlendMode`; the CPU backend reads **neither** and composites its offscreen with `PixmapPaint { opacity, ..Default::default() }`, i.e. always source-over. A `Multiply` layer would therefore multiply on Vello and not on CPU. This is a **lower-priority** divergence than the clip for two checked reasons, not by assumption: §5.2's must-match list names *clipping*, paint order, and scene geometry — **not** blend mode; and `with_blend_mode`/`with_composition` have **zero production producers** — their only two call sites (`effect_report.rs:296`, `scene_converter.rs:1061`) both sit below their module's `#[cfg(test)]` gate (lines 194 and 1001). So it is real in the backends but currently unreachable from production, unlike the layer clip, which had a live producer. Left open rather than fixed silently. **Layer transform** is ignored by *both* backends, so it does not diverge (both are incomplete, consistently).

### §6 — the window half lies; the services half works

**6-A. The §6 window model has zero production consumers, and every windowed example reaches around it to winit directly.** `obscur-windowing` (~3,100 lines) is not a dependency of `obscur-runtime` or `obscur-headless`. The port proves that a trait compiles and is object-safe; it proves nothing about §6.1–6.6 working.

**6-B. Window operations report `native()` for work not done.** `create_window` with an owner + `ApplicationModal` returns `Ok` and yields an **unowned, modeless** window — the relation never reaches `window_attributes()`. `with_constraints` is stored and never read; winit's `min_inner_size` is never called. `set_transparent` returns `native()` while `apply_properties` ignores it. `set_presentation(Exclusive)` silently degrades to borderless and reports `native()`. `activate()` always returns `Activated` without asking the compositor, so §6.3's headline rule — focus-stealing denial is *normal*, report `Denied` — is unreachable. `emulated()`/`conditional()` exist for exactly these cases and are **dead in production**.

~~**6-C. §6.6 `displays()`/`primary_display()` return nothing on every backend**, while `DisplayConverter` — a complete, correct winit→domain projection — has zero call sites and no tests.~~ — **the converter is now wired and tested; the fields winit cannot answer, and 6-A, remain open.**

"Every backend" was two, and only one of them was wrong: `NullWindowBackend` enumerates nothing *by design* and documents that its emptiness is correct. The winit backend was the finding. It now reports the real topology: `WinitAppHandler::pump` calls `pump_displays` (`winit_event_loop.rs:382`, production — the module's only `#[cfg(test)]` gate is at 504), which re-enumerates `available_monitors()` on every loop turn, mints a `DisplayId` per monitor, and projects each through `DisplayConverter` (`:384`). `displays()` / `primary_display()` (`winit_window_backend.rs:311`/`:319`, gate at 423) read that snapshot, exactly as `window()` reads a record the same handler materialized. Enumeration runs per turn rather than once at `resumed` because winit 0.30 offers no monitor notification to run on instead, and a topology refreshed once would keep describing an unplugged monitor; `record_displays` is idempotent, so an unchanged topology enqueues nothing.

**The audit called the converter "complete, correct". It was neither, and wiring it as found would have shipped two §6.6 violations:**

- It published winit's **physical** rectangle as `logical_bounds`. The two differ by exactly the scale factor, so a 2× monitor reported its logical origin at twice its true logical coordinate. Now divided (`display_converter.rs:to_logical`).
- It fabricated a `(0, 0)` origin where the topology is genuinely withheld — the one thing §6.6 makes normative ("On Wayland, *unavailable* global coordinates are represented honestly") and the one thing `Display`'s own doc forbids ("`None` … must never be conflated with a fabricated `(0, 0)` origin"). `DisplayConverter::without_global_coordinates` now leaves **both** bounds `None`: the position is what is unavailable, so the physical rectangle is no more knowable than the logical one.

  **The first fix for this was refuted, and the reason is worth keeping.** It keyed the decision off `is_wayland()`, on the stated ground that "a Wayland compositor never tells a client where an output sits, and winit answers `(0, 0)` for every monitor's `position()` there". That is false — verified in winit's source: `wayland/output.rs`'s `position()` returns `logical_position` from **xdg-output**, falling back to `wl_output.geometry`'s `location`; neither is hardcoded, and Mutter, KWin and wlroots all publish it. Withholding is a *may* in the protocol, not a rule. So the fix blanked a topology the compositor had published in full — the §6.6 rule inverted on the one platform §6.6 names, and a live regression on any Wayland desktop. §6.6's condition is **unavailability, not a platform**, and the two were conflated. The rule now reads the positions themselves: a topology is absent only when **every** monitor claims the origin, which no real multi-monitor arrangement does, and which is exactly the case winit cannot distinguish from a real origin. It needs no `cfg`, and — unlike its predecessor, which no test could reach because a `MonitorHandle` needs an event loop — the decision is a pure function over positions and is pinned by four.

**`DisplayEvent` now reaches the port**, which it did not before: winit 0.30 emits no monitor notification of any kind, so §6.6's "hotplug/configuration events" can only be *derived*, and `BackendState::record_displays` (`:145`) derives them by diffing each enumeration against the last — Connected/Disconnected/ConfigurationChanged/PrimaryChanged. Ids are keyed on monitor name + ordinal-among-same-named and deliberately **not** on geometry, so a reconfigured monitor keeps its id instead of reporting a disconnect followed by a connect.

**Tests (`display_converter.rs`, `winit_event_loop.rs`, `winit_window_backend.rs`; 19 new).** `MonitorHandle` cannot be constructed off a live event loop, so the projection was split at `MonitorSnapshot`: `MonitorSnapshot::read` holds the five accessor calls and no decisions, and `DisplayConverter::project` — every decision — is a pure function the tests drive with **real** `winit::dpi` values. **What that leaves untested is exact and unavoidable headlessly:** `MonitorSnapshot::read`'s five accessor reads, `pump_displays`'s live enumeration, and which arm of `has_global_display_coordinates` a given platform takes. Everything downstream of a monitor reading is covered.

**Still open.**

- **`available_modes`, `work_area`, and `color`/HDR stay empty** — three of §6.6's listed model fields. Two are unclosable on winit 0.30 (no reserved-region query, no color/HDR query exist); `available_modes` **is** closable via `monitor.video_modes()` and was left deliberately, because that call enumerates *exclusive-fullscreen* modes and this backend refuses to present them (`supports(ExclusiveFullscreen)` is `Limited`, degraded to borderless), so nothing downstream could act on the list.
- **6-A is untouched and still dominates this one.** `WinitWindowBackend` has **zero call sites in the entire repo** outside its own crate — not one, not even an example: the only mentions are two `pub use` re-exports in the facade and a prose sentence in `windowed_counter.rs` explaining that it creates the window *directly in `resumed`* instead. So a real display topology is now correct, projected honestly, and read by nobody. The tests are the only proof, as the audit predicted; closing 6-A is what would make this load-bearing.

**6-D. §6.7's unified Action model is architecturally precluded.** `Command`/`CommandState` are used only in their own tests. `CommandRouter` explicitly disclaims them and routes `Shortcut → InternedSymbol`. The kit's own `Menu` uses `InternedSymbol`, not `Command`. Of the spec's seven surfaces, four don't exist, one ignores the model, and shortcuts work *by bypassing it*. §6.7's only "required" — fully custom context menus — is unmet.

### §7 — the a11y tree misreports state

**7-A. A disabled control is announced as enabled and actionable.** — **CLOSED in the builder, and the outbound path is now wired; §7.1 L27's inbound path and the host's platform push remain open.** Was: `semantic_builder.rs:104-127` never read `is_disabled()`/`is_checked()`/`is_readonly()` — which exist and which **the CSS matcher already consumes** — so `SemanticState::disabled` was always false and `is_actionable()` returned **true for a disabled button**. The engine knew the truth on the CSS path and published the opposite on the a11y path.

Now the builder derives all three from the same attributes the CSS matcher reads, so the two paths agree, and the accesskit adapter already maps them (`node_converter.rs`: `disabled`→`set_disabled`, `checked`→`set_toggled`, `readonly`→`set_read_only`).

~~**Still open, and this is the finding that outlives the fix:** a real screen reader still hears nothing. `AccessKitBridge` is **never constructed outside its own crate**, and `push_accessibility`'s only caller is a test (`ui_runtime.rs:6484`).~~ — **the OUTBOUND path is now wired; the inbound one is not.**

The runtime owns the port and drives it, the way it already owns the vector decoder: `UiRuntime::set_accessibility_bridge` (`ui_runtime.rs:4687`) installs an `AccessibilityBridge`, and `run_frame` publishes to it (`ui_runtime.rs:2174`) — above the `#[cfg(test)]` gate at 5433, on the real frame path, gated on `reconciled || focus moved` so a hover frame rebuilds nothing. The facade supplies the adapter in one call: `KitBootstrap::install_accessibility` (`kit_bootstrap.rs:204`, production, gate at 325) constructs the `AccessKitBridge` and installs it, exactly where `install_vector_resources` installs SVG support; it additionally returns the `Rc<RefCell<_>>` handle, because unlike a decoder the host must reach this object to run the platform push. No demo hand-wires it. `tests/accessibility_output_path.rs` drives the real frame path into a real `AccessKitBridge` and asserts the converted `TreeUpdate` — that the disabled button arrives `set_disabled()` with no `Click` action, that focus arrives, and that the tree arrives **nested**; the adapter is an unconditional dev-dependency so a plain `cargo test --workspace` runs it.

**Found while wiring it, and it is the reason wiring matters:** `SemanticSnapshot::from_tree` dropped the tree's parent→child links, and `TreeUpdateConverter` reconstructed structure only from `Owns` relations — which `SemanticTreeBuilder` never stamps. So the projection every adapter consumes arrived **flat**: every node parented directly to the root, all nesting gone. The existing converter test (`root_gets_orphan_as_child`) asserted a 2-node tree and passed *via the orphan fallback*, so nothing caught it. The snapshot now carries its links and the converter walks them (splicing ignored nodes so a decorative wrapper does not take its content with it).

**Still open:** §7.1 L27, "accessibility actions enter the same command/event model as ordinary input" — the **inbound** path. `poll_actions` has no production caller: the runtime never drains it, so an action an assistive technology requests reaches the bridge and stops there. It is a smaller gap than it was (the tree that advertises the actions now reaches the client, and `ActionConverter::from_accesskit` already maps them), but it is unbuilt, and the two actions the builder ever advertises — `Activate`, `Focus` — are 2 of `SemanticAction`'s 14; the other 12 have no runtime equivalent to route to.

**Also noted, not fixed:** `SemanticNode::is_ignored` conflates *decorative* with *hidden*, and `SemanticState::hidden` is per-node rather than inherited, so a hidden node's children are published to AccessKit. Splicing grafts them onto the nearest visible ancestor; the pre-existing orphan fallback flung them at the root. Both announce content that is not on screen. The fix belongs in the builder (inherit `hidden` down the walk, as it already inherits `disabled`), not in the adapter.

**Also still open — what a host must supply:** installing the bridge does **not** by itself reach a screen reader. `AccessKitBridge` converts and stores; the platform push needs an OS window, which the kit never owns. A host must run `accesskit_winit`/`accesskit_unix`, feed it `last_tree_update()`, and drain `take_announcements()`. Nothing in this workspace does — no example is windowed *and* accessible — so the end-to-end claim "a screen reader hears it" is **not** verified here; what is verified is that a correct, nested, correctly-stated `TreeUpdate` is waiting at the boundary on every frame. `announce()` likewise has no runtime caller: the runtime has no live-region source to raise one from.

**7-B. ~~The headless runtime's determinism is ceremonial.~~** — closed. The root cause was structural, not a missing call: `HeadlessHost` wrapped `FramePipeline`, which is a *pure function* of `(tree, view, inputs, viewport)` with no clock and no async seam, so the host's clock and executor could not have reached a frame however they were called. The seams exist one layer up, on `UiRuntime` (`advance_motion`, `set_blocking_executor`), so `HeadlessHost` now **drives a real `UiRuntime`**:

- `advance_time` advances the clock and hands the delta *derived from the clock's own readings* to the runtime's motion scheduler, so an animation's sampled value reaches the next frame's layout and paint. `advance_time_drives_an_animation_into_the_next_frames_layout` fails (width pinned at 0) when that one line is cut; `without_advance_time_a_frame_never_moves` guards the converse.
- The host installs its `DeterministicExecutor` as the runtime's blocking port, so a frame's resource load is *queued* instead of run inline, and `run_tasks` runs it **and** drains the completion. Three tests cover it, and they fail disjointly: cutting the install fails all three, cutting only the drain fails just the two that assert the load lands.
- `DeterministicExecutor` was `RefCell`-based and therefore **not `Send + Sync`** — it could not satisfy `set_blocking_executor`'s bound at all, which is why `ui_runtime.rs`'s own tests hand-rolled a `Mutex`-based `QueuedExecutor` clone of it. It is now `Mutex`-based (single-threaded as ever) and installable.

The two vacuous tests are gone: `run_tasks_drains_the_executor` (which spawned its own closure) is replaced by the resource-load tests, and `advance_time_moves_the_clock` is kept but demoted to what it always was — a clock unit test that, verifiably, still passes with the motion wiring cut.

**Still open:** `PipelineSnapshot` into `HeadlessHost` is **not** closed by this and deliberately so — see item 7 below. `HeadlessHost::render(&View, &StyleInputs)` was removed rather than ported: pre-cascaded per-node inputs have no `UiRuntime` analogue, it had zero production callers, and every test using it only needed a populated tree (`PipelineSnapshot::capture` takes `StyleInputs` directly and is unaffected). The `Clock` port still has exactly one implementation and no system adapter: a *windowed* app drives motion by passing its own delta to `advance_motion`, so `Clock::now()`'s only reader remains `HeadlessHost::advance_time`. `counter_headless` still authors `@keyframes pulse` and only *compiles* it — the host can carry motion now, but that example was not migrated and stays motionless.

**7-C. `Subscribe` and `Inject` are accepted, acknowledged, and dropped.** ~~`serve_with_events` genuinely pushes — and has zero callers; every host uses `serve()`. **Nothing in the workspace ever constructs an `EventKind`.** A client is told `granted: true` and waits forever.~~

**Subscribe: closed, both ways round.** There are now real producers — `obscur-kit`'s `DiagnosticEventSink` (the runtime's component-failure `Diagnostic`s → `Topic::Diagnostics`) and `RuntimeEventPublisher` (real `commit_version` advances → `Topic::Frames`, real `focused()` changes → `Topic::Focus`) — and both producers are shipped in the facade (`obscur-kit`), so `EventKind`s are constructed from live runtime state rather than never. `serve_with_events` itself is still called only from **examples** (`showcase_window.rs`, `wireframe_live_window.rs`) and tests — under this audit's own Rule 1, which excludes `examples/`, that is **zero production callers**, exactly as before. What changed is that the wiring is now demonstrable and the producers are real; the kit still hands no host an events-serving DevTools by default. Where a producer does *not* exist, the endpoint now **fails closed**: `Subscribe` is answered `granted: false` unless the session is actually being driven by the pushing loop, which only that loop (crate-private, in `serve_with_events`) can assert. The demo host behind `obscur-devtools serve` has no runtime, so it denies honestly rather than hanging the client. §7.7 is untouched: the scope check still runs *first* and the new bit can only narrow a grant, never widen one (`event_push_never_loosens_the_subscribe_scope_check`).

**Still open under 7-C:**
- **`Topic::Lifecycle` has no producer.** A client may subscribe to it on a pushing host and hear nothing — granted, silent, and asserted as such (`a_subscriber_hears_nothing_from_a_topic_no_producer_feeds`). The runtime exposes no lifecycle transition stream to derive it from.
- **`Inject` is still drop-on-the-floor for the CLI.** `obscur-devtools inject` returns `Acknowledged` and nothing drains that demo host's queue; `drain_injections`/`apply_injected` are proven only from a test host (`external_client_injects_a_click_that_drives_the_runtime`), and the windowed hosts grant `observer()` — read+subscribe — so they do not accept injection at all. Untouched by this fix.
- `EventKind::Diagnostic` carries no `DiagnosticContext`, so the node/component a failure belongs to does not reach a subscriber.
- Only component-render failures reach the diagnostics topic, because only they reach `set_diagnostic_sink` (see §1-A/§1-B).

**Enforced by construction (violation is unrepresentable, not merely absent) — the strongest work in the repo:**

## Recommended order

1. **§4-A** — one absolutization pass at computed-value time retires ~8 silently-wrong rows and fixes the layout/paint disagreement.
2. **§4-B, §4-C** — both **fail open**; the two most dangerous entries here.
3. **§7-A** — ~~the a11y tree has the data and publishes the opposite; small fix, real users.~~ (done: the builder derives the state, and the frame path publishes a nested tree to an installed `AccessibilityBridge` that `KitBootstrap::install_accessibility` supplies). Still open: §7.1 L27's inbound action path, and the platform push itself, which needs a windowed host.
4. **§1-A/§1-B** — ~~a component failure should not produce stale UI and total silence~~ (done for component renders: `MountedComponent::render` goes through its `ErrorBoundary`, and `UiRuntime::set_diagnostic_sink` carries the `Diagnostic` to a real subscriber). Still open: `SubsystemRecovery` has no callers, so layout/style/renderer/resource failures neither consult a boundary nor report here.
5. **§5-B** — ~~plumb `FontRegistry`'s real metrics to `line_metrics_for`~~ (done), and give `KitBootstrap` an installer (still open — 27 examples hand-wire the stack).
6. **§6-B** — return `emulated()`/`conditional()`/`Unsupported` instead of `native()` for work not done.
7. **Wire what is already built and tested** — ~~`StylesheetCache`, the CSS→motion bridge~~ (both done: `bootstrap::CssPipeline` is the one production caller of each, and `examples/css_motion_proof.rs` proves CSS motion moves in a raster); `serve_with_events` (producers are real and shipped in the facade, but every caller is an example — zero production callers under Rule 1; see 7-C). Still open: `PipelineSnapshot` into `HeadlessHost` — and it should **not** be wired in its current shape. `capture(tree, inputs, viewport)` re-derives style → layout → scene with *fresh* coordinators from caller-supplied `StyleInputs`. Now that the host renders through `UiRuntime`, that re-derivation would silently disagree with the frame it claims to snapshot: it cannot see the motion overlay (the bindings live in the runtime), it discards the retained layout boxes, and the runtime does not even expose the `StyleInputs` a frame used — `ui_runtime.rs:2109` is the sole write to `self.inputs` and nothing reads it. Wiring it as-is would produce a confident, wrong snapshot. The real fix is to make `capture` *read* the runtime's retained stages instead of recomputing them, which changes `PipelineSnapshot`'s contract and is its own item. Every `capture` caller today is a test.
8. **Ban `Plugin → render/scene/tree` in xtask** while it costs one line.
