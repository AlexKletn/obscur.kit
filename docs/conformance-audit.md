## Why this audit exists

The previous audit called §5 "genuinely wired end-to-end" with "none" Tier-1, and recorded the "built but not wired" theme as "largely closed". Both are false, and the *reason* they are false is the finding that matters most:

> **A type existing is not evidence that anything calls it — and a doc comment asserting the wiring is how a reviewer gets convinced otherwise.**

Three doc comments in this codebase assert an architecture that is not connected:

- ~~`child_measurer.rs:19` — leaves "route to the intrinsic-measure port `IntrinsicMeasure`". They do not; `IntrinsicMeasure` has no production consumer.~~ **CLOSED by deletion.** The port, its `LayoutEnvironment` argument, its only implementation `MockIntrinsicMeasure` and its return type `IntrinsicSize` are gone — `obscur-layout/src/port/` entire plus `model/intrinsic_size.rs`, 30 files, 11 unit tests. It was deleted rather than wired because both leaf kinds already have a road and neither has the port's shape: a text leaf is intercepted before an algorithm is chosen and measured by `measure_text_node` off seventeen inputs `LayoutEnvironment`'s scale-factor-and-viewport cannot carry (`orchestration/measure_pass.rs:107`), and a replaced element is sized *before* the layout pass by `size_replaced_elements` rewriting `auto`/`auto` to the decoded image's `Px` (`runtime/resource_bridge.rs:566`). The doc this line cites now describes those two roads instead. See `docs/api/12-reality.md`, zero-caller table. **One of the three remains** — the budget one, below.
- ~~`layout_invalidation.rs:12` — "the structured replacement for scattered ad-hoc dirty flags". The shipped model *is* four booleans.~~ **Rewritten by the 3-A fix.** `layout_invalidation.rs:12` now heads a *Status: the layout phase does not consume this* section naming `layout_is_needed` as the caller that fills the accumulator and reads nothing off it. The finding it recorded is still true of layout; the doc no longer asserts otherwise. ~~Two of the three remain.~~ **One remains.**
- ~~`frame_budget.rs:15`~~ — "the emitted `Diagnostic` flows through the normal diagnostics channel". Nothing emits, and there is no channel. **Still open, but the line moved and the citation was stale**: the sentence now lives in `obscur-diagnostics/src/performance/budget_violation.doc/BudgetViolation.md:5` and `to_diagnostic.md:2`, not in `frame_budget.rs`. Re-measured — `BudgetViolation::to_diagnostic` has exactly two callers and both are tests (`runtime/frame_budget.rs:134`, inside `mod tests`, and `obscur-runtime/tests/phase_telemetry.rs:188`), so nothing routes a violation to a `DiagnosticSink` in production and the claim is as false as it was.

This audit therefore treats **"who calls it?"** as the primary question, and reports a doc that describes an unbuilt mechanism as a finding in its own right.

### The dominant pattern

**The domain crates are richer than the runtime that consumes them.** Roughly a third of `obscur-layout`, all of `obscur-system`, all of `obscur-routing`, all of `obscur-windowing`, the whole diagnostics subscription tier, the whole record/replay tier, and — until 5-C put the §5.19 policy tier on the runtime's decoded-image cache — every §5.19 cache compile, pass tests, and are called by nothing. ~~`StyleCache` and `LayoutCache` still are, and so are the three Vello caches — though those three are dead scaffolding to delete rather than a tier awaiting a consumer (5-C(a)).~~ **All five are now deleted** — the Vello three as scaffolding Vello's own atlases make redundant (5-C(a)), `StyleCache` and `LayoutCache` because the reuse they offered already ships, better keyed, as the runtime's retained `ComputedStyles` map and its `MeasureCache`/`ArrangeCache` (5-C(d)).

The structural cause is visible in one file: **`crates/facade/obscur-kit/src/lib.rs` is a re-export barrel** (lines 30–105 are `pub use X as y;` and nothing else). Anything whose only path to the outside is that file is unwired by construction. That is what hid `obscur-data-transfer` from the last audit; it now accounts for `obscur-system` and `obscur-routing` wholesale.

## Tier-1 findings

### §1 — the dynamic architecture has no execution path

**1-A. A component render failure keeps stale UI and is reported on no channel.** — **fixed for component renders.**
Was: `let Ok(view) = mounted.render(..) else { errors += 1; continue; }`, and that `continue` was the whole of §1.7. Now `MountedComponent` owns an `ErrorBoundary` built from the author's `error_boundary()` and a new `Component::fallback()`, and `render` returns `GuardedRender` — the boundary's decision, taken via `ComponentRecovery`, never a raw `Result`. `render_components` enacts it: a retry leaves the subtree and schedules the frame that spends the budget, an exhausted budget commits the fallback *over* the subtree, and a disabled boundary propagates to the nearest enclosing enabled one, whose subtree is replaced instead. `ErrorBoundaryPolicy::disabled()` now differs from enabled on every axis.

Still open, and deliberately: two paths still leave the last output standing. A **retry** does for the frames the budget buys (that is what a retry *is*), and a **propagated failure with no enclosing enabled boundary** does indefinitely — every boundary that could have answered was disabled. Both are reported; neither is silent. `SubsystemRecovery` remains uncalled, so §1.7's "layout, renderer and resource failures use subsystem-specific recovery boundaries" is still unbuilt.

**1-B. No production code in this workspace ever constructs a `Diagnostic`.** — **fixed; two producers now, one of them delivered.**
`MountedComponent::contain` builds one (via `ComponentFailure`) under a stable `view.component.props` code, and `UiRuntime::report_failure` (`ui_runtime.rs:1687`) stamps the two §1.6 fields only the runtime knows — the node it concerns and the `RecoveryAction` actually taken — before emitting to a `DiagnosticSink` installed by `set_diagnostic_sink` (`ui_runtime.rs:1758`). A test drives it through the shipped `ChannelSink`/`DiagnosticChannel` to a filtered subscriber (`ui_runtime.rs:6719`), so the §7.8 subscription path is exercised end-to-end rather than asserted. The default is a `NullDiagnosticSink`, so the failure path does not branch on whether anyone listens.

The second producer arrived with 5-A and is **built but not delivered**. `EffectFallbackReporter::report`/`report_fallbacks` (`effect_report.rs:239`, `:275`) construct real `Diagnostic`s under `render.effect.unsupported` / `render.effect.fallback`, and both backends call them from `Renderer::render` itself — `cpu_renderer.rs:328`/`:334` and `vello_renderer.rs:246`/`:254`, all far above their crates' `#[cfg(test)]` gates (1327 and 1014). This is not a theoretical path: the CPU backend's `supports_effect` (`cpu_renderer.rs:605-617`) declares `Gradient`, `Blur`, `Mask`, `BlendMode`, `BackdropFilter` and `ColorMatrix` `Unavailable`, so an ordinary gradient raises one on its first frame. But **nothing installs the sink**: `set_diagnostic_sink` on either backend (`cpu_renderer.rs:194`, `vello_renderer.rs:122`) has zero callers outside those crates' own tests, the default is a `NullDiagnosticSink` (`cpu_renderer.rs:164`, `vello_renderer.rs:96`), and the `Renderer` port carries no sink — four methods (`renderer.rs:44-91`), none an installer — so `UiRuntime` cannot install one even in principle. Every §5.2 render diagnostic is therefore built and dropped. The backend's own doc (`cpu_renderer.rs:187-193`) says exactly this, which is the honest version of the failure this audit exists to catch.

The runtime's sink still carries **only** component-render failures. Every other subsystem reports through its own path (a `BudgetViolation`, a `Result`, a last-good value); routing those through the sink is separate work.

**1-C. The kit cannot create a window (§1.4 R8).** — **CLOSED in f5ebdb8: the kit opens a window through its own port, and presents real GPU frames through it.**
Was: `WinitWindowBackend` had **zero consumers** and grew from 526 to 934 lines during this campaign without acquiring one, while six examples each called winit's `event_loop.create_window` directly. The verdict on inspection was that the port is *not* misshapen and deferred creation is *not* the blocker — it composes fine and nobody had tried. It needed one addition: `WinitWindowBackend::native_window(id) -> Option<Arc<winit::window::Window>>`, because `create_window` returns an id and wgpu needs the handle. That sits on the **adapter**, not the port — §1.1 forbids winit types leaking into the pure domain, and the host already names winit because it owns the event loop. `windowed_counter.rs` now creates through `WindowBackend::create_window` with domain `WindowProperties`, fetches the handle, and presents Vello frames; proven by a real run, and by an attended `#[ignore]`d two-window test that pins handle *identity* (a `native_window` ignoring its argument fails it).

**The audit's implied remedy was wrong, and is withdrawn.** This entry led with "`obscur-runtime` does not depend on `obscur-windowing`" as if that edge were the fix. It is not: §1.4 requires the runtime to run "headless mode without windows or GPU" and "embedded mode inside an existing host window", and §1.3 forbids linking unused backends — a runtime→windowing edge would link a window model into every headless app. **The composition point is the host**, and the missing piece was a reachable handle, not a dependency. The observation was true; the inference from it was not.

**Still open:** (a) five of six examples still hand-wire — `capabilities_window`, `controls_window`, `showcase_window`, `uikit_window`, `wireframe_live_window` — though all five need the identical trio the converted one now gets through the port; (b) **§1.4 R10 overlay mode has no representation at all** (zero hits for `overlay` in `obscur-windowing`; zero for `OverlayMode`/`OverlayHost`/`WindowKind::Overlay` repo-wide) — and adding an unconsumed enum variant would be this audit's own defect; (c) **a new silent wrongness the wiring exposed**: `WindowEvent::Resized` passes winit's **physical** pixels through while creation uses **logical** (`with_inner_size(LogicalSize::new(..))`). Both are domain `Size`, so the type system flags nothing — ask for 480×240, read back 960×480 at 2×. `windowed_counter` is correct today only because this display is scale 1. Documented and deliberately **not** pinned by a test: asserting the current behaviour would be asserting the bug.

### §2 — the primary authoring surface is unchecked

**2-A. §2.13 is unenforced where it matters.** — **PARTIALLY CLOSED: the macro enforces now, and so does the language server, which this entry had never noticed was enforcing nothing. The remaining gap is a wall, not a wire — and the entry mis-located it.**

Was: three compounding gaps: the `okui!` macro — self-declared "the spec's *primary* authoring surface" — runs **no** contract validation; the `.okui` path skips any tag with no registered contract; and `register_surface` is called only from a test, so no user component's contract can be checked. "Unknown attributes… are compile errors" holds only for the 20 hard-coded built-in tags, and only on the file path.

Now: `okui! { <Button laebl="OK"/> }` is a compile error at the author's own token, as are an undeclared `on:` event, an omitted required prop, and every §2.12 slot rule. The root was not the rule but *where it was written*: `ContractValidator::validate_element` took an `obscur_okui_syntax::ast::Element`, which this front end does not have and never will (it parses `TokenStream`s with `syn`). The rule now lives over plain data in `validation::contract_rule::check_contract`, and each front end is a thin adapter that describes its own instance and resolves a `ViolationAnchor` to its own kind of location — a byte offset for the file, a `Span` for the macro. That is the shape `check_expression` already gave §2.10. Two `okui!` documents in this repo's own tests were illegal and are now fixed, which is the check earning its keep.

**Still open, and the third gap is a wall rather than a wire:**

- **A proc-macro cannot see a user component's contract. Ever.** The macro checks `ContractRegistry::builtins()` — the primitives and widgets, whose surfaces are compiled into it. `MyProps::contract_surface()` is a function that runs when the *built crate* runs; the macro ran while that crate was being compiled. ~~The file front end takes its registry as an argument and so can be handed one; a macro has no argument to take it in.~~ **The second half of that sentence is wrong, and it hid the real shape of the wall.** The wall is not the macro's missing argument — it is that *nothing which compiles a crate can run that crate*. It binds the `.okui` **build** path exactly as hard: `build.rs` of crate X cannot call `X::CardProps::contract_surface()` either, and the edge that would let it is one cargo refuses — `[build-dependencies] X` inside X is rejected as `cyclic package dependency: package X depends on itself` (measured, not recalled). Having an argument does not help when there is nothing in scope to pass. So for the overwhelmingly common case — **a component defined in the same crate as the `.okui` file that uses it** — the file front end and the macro are equally blocked, and no *registry* wiring closes either. The argument helps in exactly two places: when the component lives in a **different** crate (a build-dependency edge is then legal and `register_surface` works), and when the consumer is a **running binary** rather than a compiler — which is what the LSP is.

  **The "Ever." needs one qualification, because it claims more than it proved.** It is exactly true of *seeing*: no front end can read a contract out of the crate it is compiling. It does **not** follow that a user contract can never be enforced there, and this round nearly let that inference stand unexamined. A front end that cannot see `CardProps` can still **emit** a check that the host crate's own `rustc` resolves — `const _: () = { fn _check(p: &CardProps) { let _ = &p.laebl; } };` alongside the generated `View` yields ``error[E0609]: no field `laebl` on type `&CardProps` … available field is: `title` `` in the same crate that defines the props (measured against real `rustc`, not recalled). Deferral, not introspection, is the mechanism this seam never considered. It is **not** proposed here and nothing is built for it: it needs a tag→Rust-type mapping (`Card` → `CardProps`) that no part of this repo has — the front ends bind a tag to a `ComponentId`, never to a type name — it reaches props-as-fields but says nothing about events, slots or allowed children, and it bypasses `ContractRegistry`/`ComponentSurface` entirely, so it is a different design rather than a wire into this one. Recorded so the wall is described by what actually holds it up.
- **`register_surface` has no in-repo caller** outside tests, and **cannot acquire one.** The entry read this as a missing wire ("a user component is checked only if a build wires it"); it is not. A production caller needs a *user component*, and this repo ships none — every component it ships is a built-in whose surface is already mirrored into `builtin_contracts`/`widget_contracts` and registered by `Compiler::new` unconditionally. `register_surface` is the seam for an application's components, and the toolkit is not an application. The honest statement is not "nobody wired it" but "the wire's other end lives in a downstream crate, and the call site is one line: `ContractRegistry::builtins().with_surface(&MyProps::contract_surface())`." There is still no auto-discovery, and there cannot be one in build.rs by the cycle above; a build-time registry would have to re-parse the crate's own Rust source with `syn` (the surface is a pure function of the derive's tokens), which is a design nothing here has proposed.
- **NEW, and worse than the entry above — now CLOSED.** The entry asserts "'Unknown attributes… are compile errors' holds only for the 20 hard-coded built-in tags, **and only on the file path**." That over-states the file path, which has *two* production consumers, not one. The second is the `.okui` **language server** (`tools/obscur-okui-lsp` — the `Analyzer`/`Server`, and the `--check` mode its own docs call "usable in a CI check"), which the entry never names. It enforced §2.13 for **nothing at all** — not one user component, and not one of the 20 built-ins either. Two independent causes, both measured: (a) `Analyzer` derived `Default`, so its registry was `ContractRegistry::default()` — *empty* — and `analyze` then called `Compiler::new(…).with_registry(self.registry.clone())`, which **replaces** the built-in seed `Compiler::new` had just installed and handed the empty one straight back; (b) every `CompileDiagnostic::Validation` was mapped to `LspSeverity::Warning`, while `--check`'s gate exits non-zero only on `Error` — so even once the rule ran, its verdict was discarded. `echo '<Button laebl="Save" bogus="1"/>' | obscur-okui-lsp --check` printed `diagnostics: none` and exited **0**, on a document `obscur-kit`'s `build.rs` panics on and `okui!` refuses at the author's own token. Both are fixed: the registry defaults to `ContractRegistry::builtins()` (matching `Compiler::new`, so the editor and the build agree by construction) and a validation failure is an `Error`, which is what §2.13 calls it in its own words. The same command now prints three located errors and exits 1; a correct document still exits 0. `a_default_analyzer_enforces_the_builtin_contracts` pins the rule running, `the_check_gate_fails_on_a_contract_violation_alone` pins the verdict counting (probed with a source that raises contract diagnostics *only*, since a `<VirtualFor each={items}>` probe would pass on its undeclared `{items}` resolution error with the whole mapping reverted), and `a_default_analyzer_leaves_correct_documents_clean` is the disjoint half. `a_user_components_registered_surface_is_enforced_by_the_editor` is the one place in this repo where `register_surface` is called for a **user** component by something that is not a compiler — and it asserts the built-ins survive the registration, because `ContractRegistry::new().with_surface(…)` silently drops them.
- **Not fixed, and named:** the LSP binary as shipped links no component crates, so its registry is the built-ins only. A host that wants its own components checked in its editor must build its own server around `Analyzer::with_registry`. That is genuinely all §2.14's "static registration is the default" can mean for a *tool* — the tool cannot discover types that are not linked into it — but it is a hand-wire, and nothing in-repo performs it outside that test. Separately, `LoweringError::MissingLoopKey` stays a `Warning` on a deliberate, pre-existing rationale ("non-fatal, spec §2.11") while `build.rs` panics on it like any other diagnostic; that disagreement is older than this round and is left standing rather than resolved in passing.
- ~~**The "skips any tag with no registered contract" gap is worse than unchecked.** `name_binding::component_id_for` resolves every unrecognised tag to `CONTAINER`, so `<Card/>` in either front end is not a mis-checked component — it is a **generic box**. No user component can be authored in `.okui` or `okui!` at all.~~ **Closed: a user component is authorable on both front ends.** `component_id_for` now takes the `TagPosition` its caller's `UiIrNodeKind` already recorded, so an unrecognised *element* tag is still the `CONTAINER` box while an unrecognised *component* tag is `user_component_id(tag)` — FNV-1a 64 of the name, lifted into a top-bit namespace disjoint from every built-in handle by construction. `<Card title="Hi"/>` mounts the registered kind, decodes its props and splices its `render` output; `okui_user_component.rs` drives that end to end through the real macro **and** the real parse→compile→lower→bridge pipeline, with a `<div>`/`<span>` sibling that must not mount.

  The §2.14 registry turned out **not** to be the blocker, and could not have been the fix: `ComponentRegistry` is a runtime value of `Box<dyn ComponentFactory>` trait objects, and codegen runs while the host crate is still compiling. The name is what the two sides share — `#[derive(Contract)]` computes the id from the same string, and now calls straight into `component_id_for` rather than its own `fnv64`, so they cannot drift. That also closed a disagreement the derive had documented and lived with: a slot's `child = "Tab"` used to name `fnv64("Tab")` while an authored `<Tab/>` carried `CONTAINER`.

  **Still open, and named:** an *unregistered* component tag is still silent. `<Crad/>` binds to its own id, mounts nothing, and — since nothing in matching, cascade, layout or paint reads a `ComponentId` — renders as the same box it always did. Making it a diagnostic is reachable on the file path (its `Compiler` takes a `ContractRegistry`) and structurally impossible in the macro, per the first bullet above; a rule stated for one front end only is the drift 2-D was written against, so it is stated for neither. `an_unregistered_component_tag_mounts_nothing` pins the residue.

  **Should `Compiler` refuse a component tag whose contract it cannot see, rather than skipping the check? Weighed, and the answer is no — on three grounds, any one of which is sufficient.** (1) *The spec does not ask for it.* §2.13's sentence is "Unknown **attributes**, events and string method names are compile errors" — a rule about the surface of a *known* component. Neither §2.13 nor §2.14 says an unregistered *tag* is an error. Refusing would be new policy wearing a spec citation. (2) *It would make the common case unauthorable.* `Compiler::new`'s registry is the built-ins, so `<Card/>` would be refused unless a build hands over Card's surface — and the cycle proven above means the build **cannot** when `Card` lives in the same crate as the `.okui` file, which is the ordinary way to write an app. The remedy would not be "wire it up", it would be "you may not author components in `.okui`". Round seven established that outcome is worse than silence. ### §3 — invalidation is per-node on the style phase, boolean-per-phase everywhere else

**3-A. §3.4 step 8 "incremental layout" does not exist.** — **CLOSED on both phases and, since this round, both halves of layout.** The style phase takes a dirty set, and so — since `f5ebdb8` — does layout; `arrange` no longer re-runs a subtree's layout algorithms to put it back where it already was.

Was: every node payload in the chain — `UiOperation::{Rerender,InvalidateStyle,InvalidateLayout}.node`, `Invalidation::node()`, `StyleInvalidation::invalidate(node,…)`, `LayoutInvalidation::invalidate(node,…)` — is **write-only**. No production reader of `is_invalidated`/`reason` exists. Both phase consumers (`StyleCoordinator::resolve`, `LayoutCoordinator::layout_editing`) take no dirty set and walk the whole tree. A hover on one node ⇒ full restyle of every node.

Now, on the interaction path only: `UiRuntime::restyle_scope` builds a `StyleInvalidation` from the nodes whose `PseudoStates` entry changed since the last styled frame; `StyleMatchingCoordinator::rematch_into` iterates it to re-match exactly those elements; `StyleCoordinator::resolve_incremental` reads **`is_invalidated`** per node to decide resolve-or-retain. A hover on a leaf resolves 1 node, not the tree — asserted by counting the runtime's own `style.resolved` telemetry, not by observing that a frame rendered (`crates/facade/obscur-kit/tests/incremental_restyle.rs`).

The scope is **`subtree(N) ∪ ⋃ subtree(S)` over N's following siblings**, which is sound rather than guessed: `MatchElement`'s entire navigation surface is `parent()` + `previous_sibling_element()`, so no matcher can read N's state from anywhere else, and `:has()` — the one selector that would reach downward, and so let N's state be read from outside the set — lowers to `PseudoClassSelector::Has`, which the matcher answers `false` for unconditionally, as it does the `of S` form of `:nth-last-child()` (both are reported as unsupported features by `obscur-css`). The selector-list pseudo-classes that *are* wired — `:is()`, `:where()`, `:not()`, `:nth-child(An+B of S)` — evaluate their arguments through the same seam, on the subject or on a preceding sibling, so they stay inside the bound. The set is downward-closed, so inheritance needs no second pass. Neutering the reach to "just the hovered node" makes `.a:hover .leaf` render **blue instead of red** — verified.

**And layout, on both halves.** `LayoutInvalidation` is no longer write-only: `layout_is_needed` is **gone**, replaced by `UiRuntime::layout_phase`, which returns a three-way `LayoutPhase::{Skip, Invalidated(LayoutInvalidation), Full}` — the accumulator the `InvalidationRouter` filled from real per-node layout-affecting style deltas. `ui_runtime.rs:2544` (production; the file's `cfg(test)` gate is at `:6695`) hands it to `LayoutCoordinator::layout_invalidated`, which classifies it **once**, via `invalidated_layout`, into the two sets the two caches need. `Full` passes `None` and drops both caches, reproducing the historical pass byte-for-byte — the same by-design correctness fallback the style half uses, on a first frame, a real reconcile, a moved viewport/scroll/editing/locale, an unrefined `FrameReason`, or a dirty root (whose `rem` base is unboundable).

*Measure* evicts exactly the `MeasureCache` entries the dirty set can have invalidated and serves every other node's size without re-measuring. The propagation is conservative rather than clever, which is what makes it sound: a dirty node evicts its **whole ancestor chain** (upward) and its **children** (downward, because a text leaf reads its container's `text-overflow`), and every unboundable case widens to a full pass — so the failure mode is a redundant re-measure, never a stale box.

*Arrange* — this round; the bullet here previously read "still not incremental — only `measure` is" — stops the walk at any node whose entire input tuple is unchanged and serves its subtree's retained absolute boxes (`ArrangeCache`, `layout_coordinator.rs:1742`) instead of re-running its layout algorithms. **Two** conditions gate it, and taking only the first would be silently wrong output rather than merely slow. `arrange` writes *absolute* positions: a node moving shifts every descendant, a sibling's growth moves every later sibling in a flow, a flex line re-flows whole — and **none of those moved nodes is dirty**, so a dirty set alone would paint them at last frame's coordinates. The gate is therefore (1) the node survived `ArrangeCache::evict` over `LayoutEviction::arranges`, **and** (2) its `ArrangeKey` — origin, constraints, containing block, viewport, scroll — matches, recomputed *fresh* by its parent's real algorithm run. Propagation is still **performed, never inferred**: a dirty node's ancestor chain re-runs in full, and that is precisely how the moved siblings' new origins are derived and their keys made to miss (`layout_coordinator.rs:2290`, production; that file's `cfg(test)` is at `:2587`).

**What arrange still costs, and it is not nothing.** A served subtree is still *walked* — `ArrangeCache::serve` copies each retained box into the frame's map — and the map is still built whole, so the pass remains O(nodes) in map inserts. Layout-algorithm runs and text shaping are the costs removed; the walk is not. Measured on the production frame path: a hover widening one of three siblings re-arranges **2** nodes of four (the hovered node and the root), and an unchanged frame re-arranges **0**.

Verified load-bearing, not vacuous, and each half falls to its own witness. The five new `layout_coordinator.rs` tests count `ArrangeCache::arranged` rather than inspecting boxes, because "the boxes are in the right place" is equally true of a full arrange. Neutering condition (2) — accept any retained entry, ignore the key — fails 3 tests, among them `a_sibling_pushed_down_by_a_grown_node_rearranges_though_it_is_clean` and the box-for-box agreement with a full pass, *while condition (1) is fully intact*: the dirty set cannot cover for the key. Neutering condition (1) — never evict — fails `a_restyle_that_only_moves_children_inside_an_unchanged_box_still_rearranges_them`, which the (2)-probe leaves **passing**: a flex container pinned to 400×100 whose `justify-content` flips moves its item without changing one bit of its own key, so the key cannot cover for the dirty set. `ui_runtime.rs`'s `a_layout_affecting_hover_rearranges_only_the_hovered_node` runs the claim through `run_due_frame`; forcing the gate off fails it.

**One thing it did not need, stated rather than dressed up.** `LayoutEviction::arranges` is the upward closure of `measures`, but `measures` already carries each dirty node's ancestor chain, so on a well-formed tree the two coincide: swapping the closure for `measures` itself passes all 5268 tests. The closure is kept because it is the *stated* reason the gate is sound — it does not rest on that coincidence surviving an edit, nor on `MAX_DEPTH` never truncating a chain — but it is defensive, not load-bearing, and the code says exactly that.

**Still open, and none of it is incidental:**

- **§4.3's declared mechanism is still not the one that ships, and its types are still unconsumed.** `LayoutContext`, `LayoutDependency` and `LayoutContainment` have **no production constructor at all** — `LayoutContext::new`'s only call site is `layout_invalidation.rs:196`, below that file's `cfg(test)` at `:189`, and every `dependency_mut()` call is likewise test-only. So `should_remeasure`, and the `LayoutInvalidation::note_{constraints_changed,child_changed,upward}` gates built on it, answer for a dependency graph nothing fills in. The shipped path reaches §4.3's two rules by other means (downward exact in the cache key; upward by ancestor-chain eviction), and the **containment stop is unimplemented** — nothing narrows that eviction. `layout_dependency.rs:10`'s "structured replacement for scattered ad-hoc dirty flags" claim — which had merely *moved* there from `layout_invalidation.rs:12` when that file was corrected — and `layout_context.rs`'s matching claim now both state that they are contracts for a consumer that does not exist.

Hovering inside a large subtree restyles that subtree even when no rule mentions `:hover`.

### §4 — relative units die at the layout↔paint seam

**4-A. `font-size: 2rem` renders at 16px, and poisons every `em` on the node.** — **CLOSED for `em`/`rem`/`vw`/`vh`/`vmin`/`vmax`, and for the one `%` that reached paint (`border-radius`); still open for `ch`.** Was: `ComputedStyle` never absolutized lengths — layout resolved via `resolve_px(ctx)` while paint read the same property through `as_px()` (absolute px only), so `border-width: .1em` **reserved layout space and painted nothing** and the two phases disagreed about the same box.

Now: `computed/absolutize.rs` is the one fold, and `StyleResolver::resolve` runs it over every computed property (`style_resolver.rs:633`) against a `LengthContext` built from the `font-size` resolved one step earlier (`:613-623`) — so paint's `as_px()` reads became *correct* rather than being removed. The match is exhaustive rather than wildcarded, so a new length-bearing `PropertyValue` variant cannot quietly opt out and reintroduce the seam. `tests/relative_units_paint.rs` asserts against the **published `DisplayList`**, never a hand-built scene: `2rem` paints at 32, an `.1em` border paints exactly the 4px edge layout reserved (and the identical edge its `4px` control paints), `box-shadow: 1em .5rem 1vw 2px` lands on offset `(20, 8)` / blur `4`, and `10vw` vs `10vh` read different axes on a deliberately non-square viewport. Neutering the fold fails 6 of its 10 tests.

**`border-radius: 50%` — the circle idiom — is now CLOSED**, and it is the one `%` that ever reached this seam. (`border-*-width` takes no percentage; `font-size: 50%` never had this bug — `absolute_font_size` resolves it against the parent's size via `with_percent_basis`. A `%` on a *layout* property is resolved by layout against its containing block, which is not this seam.)

Was: a `%` is deliberately not absolutized (its basis is the box, which layout has not produced), and `corner_radii_of` read the computed length through `Length::as_px` without the `bounds` it would need, yielding `0` — a square corner. The two things it needed are both built. (1) **A `CornerRadii` that carries two radii per corner**: `CornerRadius { x, y }` (`corner_radii.rs`) makes a corner the *quarter ellipse* CSS Backgrounds 3 §4.1 actually defines, and `Path::rounded_rect` drives each axis from its own radius, so the ellipse survives into the outline. (2) **Percentage resolution in paint**: `corner_radius_of` (`scene_coordinator.rs`) resolves a `Percent` per axis against the arranged border box — §4.1's "percentages for the horizontal radius refer to the width of the border box, whereas percentages for the vertical radius refer to the height" — so `50%` on a 200×100 box is `(100, 50)`, an ellipse, and a circle only when the box is square. Resolution and the §4.5 overlapping-curves correction both run **once**, at the single point the radii are derived, so every consumer (background fill, subtree clip, border ring, shadow, outline) sees the same resolved radii.

`normalized` implements §4.5 verbatim (`f = min(Li/Si)`, one scale applied to *all* corners) rather than the old per-corner `min(w,h)/2` clamp, which is what makes `50%` survive: every side sum equals that side's length exactly, so `f == 1` and the authored ellipse is left alone. Proven by `border_radius_fifty_percent_paints_an_ellipse_on_a_nonsquare_box`, which drives the real `SceneCoordinator` and reads the radii off the emitted path's anchors — a case no scalar radius can express. Neutering the two halves fails them **disjointly**: resolving both axes against the width fails both it and `percent_radius_resolves_per_axis_against_the_border_box`; making the path builder use one axis fails only the paint test. `clip_cross_backend.rs` pins that both backends admit the same points for an elliptical clip (§5.2) — though note its *agreement* assertion cannot catch a defect in the shared `Path::rounded_rect`, which would make both backends wrong together; only its expected values can, and they are chosen to sit where a scalar radius and a true ellipse actually disagree.

**Still open — the seam is closed for the units that fold, not for the one that does not:**

- ~~**`ch` still dies at the seam, exactly as `em` did.** `Length::absolutize` leaves `Ch` symbolic when `ctx.ch_width` is `None` (`length.rs:129`), and the resolver's context never carries one. Only **layout** measures the `0` glyph. Measured at HEAD: `.box{width:100px;font-size:40px;border-style:solid;border-width:1ch}` arranges a **148px** border box and paints a **0px** edge.~~ **CLOSED: the measurement is threaded into computed-value time, so `ch` folds where every other unit does.**

  **Direction matters, and the spec is narrower than it first reads.** §6.1.1 names two triggers — an outer shadow whose radius is under a *positive* spread, and an inner shadow whose radius is under "the absolute value of a negative spread distance". ### §5 — font subsystem real but Linux-only; one cache bounded, the rest dead; diagnostics emitted into a null sink

Vello: `Mask` → `Unavailable` (its coverage is applied by neither backend), `Blur`/`ColorMatrix`/`Text` → `Limited` (a *nested* filter layer draws unfiltered; an unregistered font's run is skipped). `HeadlessRenderer` claimed `Emulated` for everything while rasterizing nothing at all; it now answers `Unavailable`, like every other null object here. Both backends' render paths call `unsupported_effects` against their own table and emit `RendererError::UnsupportedEffect` — constructed, on the production path — into their `DiagnosticSink`, once per effect. (That sink is a `NullDiagnosticSink` in every in-tree path; see the delivery caveat below, which qualifies this entire entry.)

One arm of that table was itself the finding reproduced, caught by the verifier and corrected: Vello answered `BlendMode → Native`, but `SceneEffect::BlendMode` names **two** inputs and `push_layer` honours one. A layer's `blend_mode()` *field* becomes a peniko `Mix`; a `LayerEffect::Blend` in the layer's *effects list* is dropped, because that list is scanned only for `Blur` and `ColorMatrix` — a parameter on the floor, reported as supported. It is now `Limited`, with the split named. The deeper problem is the domain's, and is left open: **`LayerEffect::Blend` duplicates `SceneLayer::blend_mode` and has zero producers anywhere** — a dead variant that no backend honours, which is why one conflated table arm could cover both and read as true. CPU had it right (`Unavailable`) throughout.

**The "and fallbacks" half is now emitted for text, and only for text.** It was previously met by declaration alone — the diagnostic fired only for `Unavailable`, while a `Limited` effect's restriction was merely queryable on `supports_effect`. The two halves are found differently, which is why one scan could not cover both: `Unavailable` is a property of the **backend** (the effect never happens, whatever the frame), so the table answers it; a fallback is a property of the **frame** (a `Limited` effect draws correctly until the input its restriction names is missing), so only the backend, drawing that scene, can say it bit. `EffectFallback` / `EFFECT_FALLBACK` (`render.effect.fallback`, a distinct code from `render.effect.unsupported`, so a host can route them apart) is emitted from both render paths, deduplicated per effect **and reason** — two runs missing two different fonts are two reports; the same gap every frame is one.

`Text` was chosen because it is the only `Limited` arm on **both** backends, it is runtime-conditional, and its Vello form is the costliest thing here to discover by looking: an uncovered run is **dropped in silence**, so there is no artifact on screen to notice. Each backend's scan mirrors **its own** paint path rather than a shared guess — CPU demands an exact registry hit whose bytes `skrifa` accepts (`has_outlines_for`), Vello mirrors `font_for`, which falls back to the primary id `0` (`can_draw_text`) — because a scan that disagrees with the paint path reports a fallback that did not happen, or stays quiet about one that did, which is the defect this diagnostic exists to end. Both are pinned by tests that fail disjointly when each half is neutered.

**Still open — the `Limited` arms that remain declared, not emitted.** Naming them, because "fallbacks are explicit diagnostics" is *not* fully met: Vello's `Blur`/`ColorMatrix` (a **nested** filter layer is drawn unfiltered — the converter would have to report that it could not peel the layer, which it currently does not track); Vello's `BlendMode` (a `LayerEffect::Blend` is dropped — undiagnosed, though the variant has zero producers anywhere); and CPU's `Clip` `Emulated` allocation-failure path, which falls back to the parent mask silently. CPU's `Shadow` is the one `Limited` arm needing nothing further: `blur` is its **only** dropped parameter (`spread`/`offset`/`inset`/`radii`/`color` are all forwarded — verified against the arm, not assumed), and `Blur → Unavailable` already emits whenever the radius is positive.

**Still open — Vello's text scan is narrower than the CPU's, and deliberately so.** `can_draw_text` is a registry lookup that does not parse, because `font_for` does not parse: registering **unparseable** bytes satisfies the scan and raises nothing. Worse than un-diagnosed, that case **panics** — `vello::DrawGlyphs::draw` (vello-0.9 `scene.rs:626`) unwraps `FontRef::from_index`, so a host that registers junk bytes crashes the backend rather than degrading. That is a pre-existing robustness bug, independent of this entry (nothing here touches the draw path), found by a test that tried to register junk; it is **not fixed**. The CPU backend has no such hole — it parse-checks, and its scan mirrors that.

**Still open — and this qualifies the whole entry: no in-tree code installs a renderer sink, so today every one of these diagnostics lands in a `NullDiagnosticSink`.** The construction is real and on the production path — that much this entry's first round got right — but "reaches a host `DiagnosticSink`" overstated the delivery, and the check is the campaign's own rule: every call to `CpuRenderer::set_diagnostic_sink` / `VelloRenderer::set_diagnostic_sink` sits below its module's `#[cfg(test)]` gate (`cpu_renderer.rs:1327`, `vello_renderer.rs:1014`); no example, host, or runtime calls either. But "explicitly diagnosable" is, in this tree, *reachable* rather than *reached*. **Still open — the vocabulary covers effects, not every compositing parameter:** `SceneLayer::transform()` and `LayerEffect::Opacity` are read by **neither** backend, and the Porter-Duff `composition` is honored by Vello but dropped by the CPU — none of the three is diagnosable through the table or either scan. **5-C. §5.19 is a complete, tested, entirely unused subsystem.** ~1,150 lines (`PathCache`/`GlyphCache`/`TextureCache`, `CacheBudget`/`EvictionPolicy`/`CacheStatistics`/`VisibilityPriority`) with zero consumers. The caches that run are unbounded `HashMap`s with no budget, eviction, metrics or test switch. — **PARTLY CLOSED: the policy tier (`obscur_resources::cache`) now runs on one production cache — the runtime's decoded images, which is where the bytes are. ~~The three Vello caches are untouched and still have zero consumers~~ — **they are now deleted** (see (a) below); they needed no budget, because they held nothing on any path and two of them cached work Vello itself does and already bounds, so they were dead code to delete rather than §5.19 work outstanding. The finding's premise about the text caches was also wrong, and the reason is a real shape mismatch. All stated below.**

**What the tier now bounds.** `UiRuntime::image_cache` was `HashMap<Box<str>, SceneImage>` — decoded RGBA8, `w × h × 4` bytes per URL, inserted by `resolve_background_images`/`resolve_element_images` and **never removed** except by a wholesale `clear()` on a provider swap. Every distinct image an app ever showed stayed resident for the life of the process; that is the "grows without limit" the finding names, and it was the only live cache with unbounded *bytes*. It is now `runtime/image_cache.rs`, which composes the domain tier rather than reimplementing it: `CacheBudget` rules admission, `EvictionPolicy` picks the victim from `CacheEntry` bookkeeping, `CacheStatistics` carries live bytes/entries plus hit/miss/eviction counters, and `CacheKey::for_resource(handle.id())` reuses the `ResourceId` the hub already minted per URL. Those counters now reach a client: the §7.6 `Caches` inspectable reports resident bytes and the hit/miss/eviction totals, not just a count — the first pass wired the metrics to a getter (`image_cache_statistics()`) whose only caller was a test, which is the same *affordance, not a report* this audit charges against `idealized_line_metrics()` in 5-B(c), and the verifier caught it. `set_image_cache_budget` / `image_cache_budget` / `set_image_eviction_policy` / `image_cache_statistics` are the host surface. **The default is `CacheBudget::unlimited`**, so a host that asks for nothing gets byte-identical behaviour to before.

Two things make it a cache rather than a leak with a counter. Eviction **releases the hub handle**: `image_handles` is the "already requested, do not retry" guard, so an evicted URL left in it would silently never paint again — `release_evicted` is what lets a still-referenced image reload. And `mark_image_visibility` scores every resident URL against the frame's own boxes and viewport each compose, so `VisibilityPriority` is derived from real geometry, not defaulted: eviction drops what nothing is showing before what the frame is painting.

`crates/facade/obscur-kit/tests/image_cache_budget.rs` proves it from outside: real PNGs, the real `FsResourceLoader`, the real decoder, real `render_now` frames, and **no test touches the cache** — every insert and eviction is a side effect of composing. Reverting each half fails it disjointly (budget → the budget + visibility tests; visibility marking → only the visibility test; handle release → only the reload test). The visibility test is not a coin flip: document order makes the off-screen image the *more recently used* of the two, so recency alone would evict the visible one.

**Still open — this closes one cache, not §5.19.**

(a) **`PathCache`/`GlyphCache`/`TextureCache` were exactly as unused as the finding says — dead code, not a §5.19 gap, and the reason this entry previously gave was wrong. They are deleted; the analysis is kept because it is why.** Zero consumers, verified: every mention outside `crates/adapters/obscur-render-vello/src/cache/` is inside that module's own `#[cfg(test)]`. They are unbounded `HashMap<u64, V>` newtypes implementing *none* of §5.19, and having the right names is not having the right interface. But §5.19's list is permissive — "runtime caches **may** include … paths; glyphs; … textures" — and its requirements bind the caches that *run*. None of these three is ever constructed on a live path, so none holds a byte and a budget on them would bound nothing. **Applying the tier here would itself be the defect this audit exists to name: policy wired to a cache with no producer.**

This entry said the blocker was that "the Vello backend builds a fresh `Scene` every frame and holds nothing across frames". **That is false.** `VelloRenderer` (`renderer/vello_renderer.rs:44-70`) keeps its `blitter`, `blur` and `color_matrix` pipelines across frames, and `SceneConverter` (`conversion/scene_converter.rs:162`) keeps the host's registered fonts. All are bounded by construction — at most one pipeline each, and the font map is a host registry, not a content-keyed cache. Renderer statefulness was never the blocker. The real one, for two of the three, is that **the cached value has no producer in this crate**, so making the renderer stateful would give them nothing to hold:

- `TextureCache` holds a `wgpu::Texture` per image; this adapter never creates one. `draw_image` (`scene_converter.rs:890-977`) wraps the decoded pixels in a `peniko::ImageData` and calls `Scene::draw_image`, which takes image *data*, not a texture (`vello-0.9.0/src/scene.rs:443`); Vello uploads it into **its own** `image_atlas` (`vello-0.9.0/src/lib.rs:333`), keyed by the blob id. Filling this map means taking image residency back from Vello via `Renderer::override_image`.
- `GlyphCache` holds rasterized coverage per glyph; this adapter never rasterizes one. Runs arrive pre-shaped from `obscur-text` and go to `Scene::draw_glyphs` (`scene_converter.rs:501`); `vello_encoding` runs its own `GlyphCache` (`vello_encoding-0.9.0/src/resolve.rs:159`) and **already prunes it** by age (`vello_encoding-0.9.0/src/glyph_cache.rs`: `MAX_ENTRY_AGE = 64`, `CACHED_COUNT_THRESHOLD = 256`, pruned every 64 resolve phases). Filling this map would duplicate a cache the dependency already keeps *and bounds*.
- `PathCache` is the only one whose value this adapter does produce (`PathConverter` makes the `BezPath`s). It still has no key: nothing hashes a path's geometry, and `obscur_scene::Path` (`path/path.rs:16-17`) derives `PartialEq` but not `Hash` — holding floats, it cannot derive one — so the `u64` would need a bespoke bit-level hash written for the purpose. Nothing has measured path conversion as a cost worth that.

Re-verified immediately before removal that no `.rs` line outside the module named any of the three, including the facade barrel and the prelude, and re-verified the redundancy against the dependency's own source rather than against this entry. The reasoning above is preserved as a comment at the deletion site in `obscur-render-vello/src/lib.rs` — the same shape as the `StaleResult` record in `obscur-task/src/task/mod.rs`, because the code cannot carry it: the code is its absence. **5-D. `Clip::Mask` does the opposite thing on each backend** — CPU shows the content, Vello hides it — and **no cross-backend golden test exists** to catch it. §5.2 names clipping as a must-match property. — **CLOSED: `Clip::Mask`, plus two sibling divergences (empty-path clip, and the layer clip the CPU ignored). Mask *coverage* and layer blend mode remain open, both stated below.**

The domain settles which backend was right. A `Mask` "does **not** carry the source itself" (`mask.rs:8`), and `Clip::bounds()` is `None` for a mask because "a mask's extent depends on its source content, **which is not known to the clip itself**" (`clip.rs:58-59`). A mask clip states *no extent*, so a backend may not invent one — least of all the empty extent, which discards the content. **CPU was right; Vello was wrong** (`clip_converter.rs:50`, `Clip::Mask(_) => BezPath::new()`). Vello's own `push_layer` already used an unbounded rect for a mask, so the file contradicted itself, and the converter's doc claimed "an empty shape clips away nothing" — the exact opposite of what Vello does with one. Vello's mask clip now resolves to that same unbounded outline, and both of its clip paths route through one rule instead of two.

**Sibling found and fixed (reverse polarity).** An **empty/degenerate path clip** diverged the same way and the correct answer is the *opposite*: the CPU inherited the parent clip and painted (`cpu_renderer.rs`, `to_sk_path` → `None` → `parent.cloned()`) while Vello admitted nothing. Here the extent *is* stated, and stated to be empty, so nothing may pass — Vello was right and the CPU now pushes an all-zero mask. "No bounds known" (mask) and "bounds known to be empty" (empty path) are opposite instructions that both reach a backend as an absence, which is how one line served both. A zero-area *line* path and a zero-size *rect* already agreed (both admit nothing); only the `to_sk_path` → `None` cases diverged.

**The missing test now exists**, and it is the half that matters: `crates/facade/obscur-kit/tests/clip_cross_backend.rs` drives the same scene through both backends across every `Clip` variant and asserts they agree *and* that the shared answer is the one the domain requires. Both backends are wired as **unconditional dev-dependencies** of `obscur-kit` — `render-vello` is not a default feature, so a feature-gated test would be skipped by a plain `cargo test --workspace`, which is the silence that let this bug live. Reverting each half fails it disjointly.

**What the test does not cover:** it compares Vello's *clip geometry* against the CPU's *rasterized coverage*, not Vello pixels against CPU pixels. Vello's rasterizer needs a GPU and this workspace has **no GPU test target at all** (every GPU proof in `obscur-kit` is a hand-run `[[example]]`), so a readback `#[test]` would silently no-op on GPU-less CI. §5.2 puts rasterization/AA in *allowed differences* and clipping/scene-geometry in *must match*, so the GPU-free clip decision is the property §5.2 actually constrains — but this is a real gap, not a complete golden test. Clip **nesting** and paint order are not compared either.

**7-B. ~~The headless runtime's determinism is ceremonial.~~** — closed.
