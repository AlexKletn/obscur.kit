# Соглашение о качестве кода

[English version](CODE_QUALITY.md)

- **Одна сущность на файл.** Держите тип, его реализации, методы и внутренние вспомогательные функции в одном файле. Выносите в отдельный файл самостоятельный тип, состояние, владельца ресурса или обработчик, если у этой сущности своя зона ответственности.
- Размещайте тесты в отдельном файле `<name>.tests.<ext>` рядом с `<name>.<ext>`, где принято такое соглашение. Для Rust следуйте [структуре исходников крейтов](specs/obscur-kit-2-crate-architecture/03-source-layout-by-crate.md), которая хранит модульные тесты вместе с сущностью.
- **Объединяйте файлы одного домена в модуль.** В `lib.rs` и `mod.rs` оставляйте только объявления модулей и реэкспорты.
- **Давайте имена, которые раскрывают назначение.** Используйте один и тот же термин для одного понятия во всей кодовой базе.
- **Одна задача на функцию.**
- **Храните общие правила в одном месте.** Объединяйте логику, которую нужно менять одновременно.
- **Объясняйте в комментариях, почему принято решение.** Описывайте ограничения и решения, которые трудно понять из кода.
- **Код должен сам объяснять, что он делает.**
- **Снижайте когнитивную нагрузку.** Выбирайте прямолинейные решения. Избегайте хитрых приёмов, из-за которых приходится разгадывать порядок выполнения или движение данных.
- **Запрещено описывать в комментариях, что делает код.**
- **Обрабатывайте ошибки там, где можете на них отреагировать.** При передаче ошибки вызывающему коду сохраняйте её исходную причину.
- **У каждого ресурса есть владелец.** Из кода должно быть понятно, кто освобождает память, закрывает дескриптор или снимает блокировку.
- **Оставляйте состояние согласованным при ошибке.** Если операция выполнилась частично, откатите изменения или явно сообщите вызывающему коду, что успело выполниться.
- **Зафиксируйте правила доступа к общему состоянию.** Для изменяемых данных должно быть ясно, кто может их менять, какая синхронизация нужна и в каком порядке брать несколько блокировок.
- **Указывайте единицы измерения и проверяйте диапазоны.** По именам или типам должно быть видно, где байты, страницы и такты. Проверяйте переполнение при вычислении размеров и смещений.
- **Проверяйте пути отказа.** Тестируйте частичную инициализацию и отказ после захвата ресурса. Проверяйте и результат операции, и освобождение ресурсов.
- **Документируйте инварианты безопасности.** Рядом с каждой `unsafe`-операцией укажите, какие условия делают её безопасной.
