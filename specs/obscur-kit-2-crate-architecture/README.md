## Ключевая схема

```text
foundation
    ↓
domain
    ↓
application/runtime
    ↓
ports
    ↑
adapters
    ↑
facades/frontends/tools
```

Порты принадлежат тем доменам и application services, которые ими пользуются. Отдельные `*-api` крейты создаются только для действительно устойчивых внешних границ: renderer, UI IR, diagnostics protocol и plugin API.

## Основные правила

- Крейт соответствует bounded context, независимой feature/dependency boundary, target boundary либо стабильному protocol/API/ABI.
- Один файл содержит одну главную сущность и её `impl`; связанные, но самостоятельные сущности получают собственные файлы.
- `mod.rs` и `lib.rs` не содержат алгоритмов и сущностей — только документацию уровня крейта, объявления модулей и реэкспорты.
- Не создаются свалки `common`, `utils`, `shared`, `types`, `models`, `helpers`.
- Типы Winit, wgpu, Vello, AccessKit, Wasmtime, Tokio и других adapters не попадают в доменные публичные API.
- Retained tree остаётся единственным владельцем UI-идентичности.
- Runtime оркестрирует домены, но не владеет процессом приложения.
- Все тяжёлые и платформенные реализации заменяемы через узкие порты.

## Целевая и стартовая структуры

Документы описывают целевой workspace. Не следует создавать десятки пустых крейтов заранее. Новый крейт выделяется, когда выполняется хотя бы одно условие:

1. самостоятельный bounded context;
2. отдельная feature/dependency boundary;
3. отдельный target или platform adapter;
4. стабильная публичная, protocol- или ABI-граница;
5. независимая компиляция и тестирование действительно полезны;
6. тяжёлую зависимость необходимо физически исключать из сборки.
